# CSV Viewer — VS Code extension spec (v0.3)

Read-only table viewer for CSV/TSV files. Works in VS Code and its forks (Cursor, Windsurf) — target Open VSX + VS Code Marketplace, `engines.vscode: ^1.80.0`.

## Core features

### 1. Column visibility: table vs detail
- Each column is either **shown in table** or **detail-only**.
- Every table row has an expand chevron (and clicking the row toggles it). Expanded row shows a detail panel below it: key/value list of all **detail-only** columns for that row (label = header, value = cell, preserve newlines, wrap long text). If no columns are hidden, the detail panel shows all columns.
- **Columns** button in toolbar opens a popover: checkbox per column (checked = in table), a search box to filter the list, "Show all" / "Hide all" buttons, and drag-free up/down ordering is NOT required.
- Header context: right-click header → "Move to detail" (hide) is nice-to-have, skip if costly.
- Default visibility when a file is first opened: first N columns in table (setting `csvViewer.defaultTableColumns`, default 8), rest detail-only.
- Persist column visibility per file (keyed by file URI) in `workspaceState`. If the header row changes, the map is **merged**, not replaced: every previously-known column's setting is kept (even for a name the *current* header list no longer has), and only the current header list decides what's actually shown/hidden right now. This is what makes a setting survive an intermediate reconciliation against a *different* header set — e.g. toggling "first row is header" off (synthesizing `column_1..N` headers) and back on — instead of being silently dropped and reset to the default rule. New columns follow the default rule.
- `ColumnVisibilityMap` is safe for any header name, including `__proto__`, `constructor`, `toString`, and `hasOwnProperty` — `src/core/columns.ts` writes every entry via `Object.defineProperty` (which bypasses `Object.prototype`'s `__proto__` accessor, whose setter otherwise silently no-ops for a non-object value) and reads only via `Object.prototype.hasOwnProperty.call` plus a `getVisibility` helper, never a bare `map[header]`. Already-persisted plain-object maps keep working: `JSON.parse` (the shape `workspaceState` round-trips through) creates a genuine own `"__proto__"` property per the JSON spec, unlike a runtime `obj["__proto__"] = x` bracket assignment.
- "Expand page" / "Collapse page" toolbar buttons — apply to the current page's rows only (see Pagination below).

### 2. Filtering (include + exclude)
- Toolbar: global quick search box (case-insensitive substring over all columns, debounced ~150ms). "Case-insensitive" here means the shared `foldCase` (below), not plain `toLowerCase()`.
- **Filter rules** panel: list of rules, add/remove. Each rule:
  - column: any single column, or "(any column)"
  - operator: `contains`, `equals`, `starts with`, `ends with`, `regex`, `is empty`, `>`, `<`, `>=`, `<=` (numeric operators compare as numbers via the shared `parseNumber`, below; row fails if cell isn't numeric)
  - value (hidden for `is empty`)
  - mode toggle: **Include** / **Exclude** (exclude = row is dropped if it matches)
  - case-sensitive toggle (default off)
  - enabled checkbox (temporarily disable without deleting)
- All enabled, **active** rules combine with AND (include rules must all match; any matching exclude rule drops the row). A rule is **active** exactly when `isRuleActive(rule, headers)` (`src/core/filter.ts`) says so — the single helper both `applyFilters` and the filter panel UI use, so they always agree:
  - Invalid regex → rule shown in error state (outlined, "Invalid regex — rule ignored") and ignored, never crashes.
  - **Column no longer exists** (e.g. after a header rename or a separator change that changes the column count) → rule shown in the same error state ("Column not found — rule ignored") and ignored — i.e. it has *no effect*, not "matches nothing." An ignored include rule leaves every row as-is; the pre-fix behavior of treating a missing column as "matches nothing" meant one stale include rule could silently hide the entire file.
  - **Empty value** on any operator except `is empty` (which takes no value) → rule shown in a subtler hint state (dashed outline, "Enter a value — rule ignored") and ignored, for the same reason: an empty value's incidental per-operator behavior (e.g. `contains ""` matching everything, `equals ""` matching only truly-empty cells) isn't a well-defined "the user meant this," so the rule does nothing until a value is entered.
- Case-insensitive matching (every string operator above, and quick search) uses a shared `foldCase(s)` (`src/core/caseFold.ts`): `toLowerCase()`, then drop the combining dot above (U+0307) that follows an "i" (so Turkish `İ` folds to plain `i`, not `i` + a stray combining mark), then fold `ß` → `ss` (so `STRASSE` matches `straße`). No accent-stripping beyond those two rules.
- Numeric operators use a shared `parseNumber(s)` (`src/core/number.ts`, also used by sort — see below): trim, then accept only `/^[+-]?(\d+(\.\d*)?|\.\d+)([eE][+-]?\d+)?$/`. This is stricter than plain `Number()`: it rejects hex (`0x10`), `Infinity`/`NaN` text, thousands separators (`1,000`), and currency/percent symbols (`$5`, `5%`); `1e3` (scientific notation) still parses.
- Quick-add: in expanded detail or table cell, right-click a cell value → "Filter: include this value" / "Filter: exclude this value" (creates `equals` rule). Nice-to-have; implement if straightforward via a small custom context menu in the webview.
- Status bar in webview: "Showing X of Y rows".
- Persist filter rules per file alongside column settings.

### 3. Sort
- Click a table header: cycles asc → desc → none. Shift+click adds secondary sort keys (multi-sort); indicator shows direction and priority number when >1 key.
- Also sortable by detail-only columns via a "Sort by…" dropdown in the toolbar (since hidden columns have no header).
- Type-aware comparison, computed as one canonical sort key per cell per sort column, up front (not re-derived per pairwise comparison — see below): a value is **empty** (always sorts last, in both directions), **numeric** (parses via the shared `parseNumber`, above), or **text** (everything else, compared via a shared `Intl.Collator(undefined, { numeric: true, sensitivity: "base" })`). Within a kind, numeric compares by value and text by the collator, both direction-adjusted; across kinds, numeric sorts before text in ascending order and after text in descending order (so direction still flips the *relative* ordering of numeric vs. text, same as it flips numeric-vs-numeric and text-vs-text). Stable sort (original row order breaks ties).
  - This precompute-once design is also what makes the comparator a genuine total order: deriving "is this numeric?" independently for each pairwise comparison (the pre-fix design) could put two numerically-tied values (e.g. `"10"` and `"1e1"`) on opposite sides of a third, non-numeric value, since each comparison against that third value fell back to string collation independently and didn't have to agree with the other. A precomputed key removes that inconsistency by construction.
  - Performance: sorting 500k rows × 20 columns on 3 keys stays well under 1.2s (measured ~0.8s), including resolving each text column's collation rank once per distinct value rather than calling the collator again for every comparison.
- Persist sort per file.

### 4. Pagination
- A pager bar sits below the table, always visible (the table area scrolls between the toolbar/status-bar and the pager, not the pager itself). Controls, left to right: First «, Prev ‹, "Page [ N ] of M" (N is a number input — Enter or blur jumps, clamps to 1..M, invalid input restores the current page), Next ›, Last », "Rows X–Y of Z" (Z = filtered count; "No matching rows" when Z = 0), and a page size select (25/50/100/200/500, default 100).
- Nav buttons disable via the `disabled` attribute when not applicable (First/Prev on page 1, Next/Last on the last page; all four when Z = 0).
- The top status text "Showing X of Y rows" is unaffected by pagination — it always reflects the full filtered count, not the current page.
- Page resets to 1 on quick search, filter rule, and sort changes. Column visibility changes and expand/collapse keep the current page. A live reload (`load` for the same fileKey) keeps the current page, clamped to the new page count.
- Changing page size keeps the first row currently shown visible: new page = `floor(firstRowIndex / newSize) + 1`. Changing page scrolls the table area back to top.
- "Expand all" / "Collapse all" (labeled "Expand page" / "Collapse page") apply to the current page's rows only; expanded state is keyed by row id, so it survives paging back and forth.
- Keyboard: Alt+→ / Alt+← move to the next/previous page when focus isn't in an input/select/textarea (so native text navigation and scrolling keys are untouched).
- `pageSize` is persisted per file as part of the view state; the current page number is not. A missing/invalid stored value (state saved before pagination existed) falls back to 100.
- Pure logic lives in `src/core/paging.ts` (`pageCount`, `clampPage`, `pageSlice`, `pageForRow`, `normalizePageSize`) — no DOM/vscode imports, unit-tested like the rest of `src/core`.

## Parsing
- `src/core/csvParse.ts` (pure module, no vscode/DOM import) wraps [Papa Parse](https://www.papaparse.com/) as the tokenizer: quote-aware (`"` only opens a quoted field as the first character of a field — a stray mid-field `"`, e.g. an inch mark or `He said "hi"`, is literal text, not a quote-open), `""` escapes, newlines inside quotes, CRLF/LF/CR, BOM stripping, ragged rows (pad short rows with "", extra cells get auto headers `column_N`).
- **Line endings are normalized before Papa ever sees the text**: every `\r\n` and lone `\r` is converted to `\n` first. Papa sniffs a single newline style for the whole file from an early sample and then treats any *other* line-ending style as literal text rather than a row separator, so a file mixing CRLF/LF/CR (which real-world CSVs exported by different tools/OSes routinely do) used to silently merge rows and leak newline characters into cell values. Normalizing up front fixes that for the whole file — including inside quoted fields, so an embedded CRLF in a quoted field is now stored as LF. That's a deliberate, documented tradeoff (there's no way to tell "a CRLF that's part of quoted content" from "a CRLF that separates rows" without a full parse pass), not an oversight.
- `parseCsv(text, options)` public API: BOM strip, header dedupe (`name`, `name_2`, guaranteed collision-free against every other final header — see below), empty header → `column_N`, ragged-row padding, extra cells → `column_N` headers, `firstRowIsHeader` option, and a new `quotes` option (default `true`). It returns `{ headers, rows, delimiter, quoteProblems }`: `delimiter` is the delimiter actually used (from Papa's `ParseResult.delimiter`), so the UI can show it (e.g. "Auto (;)"); `quoteProblems` is covered below.
- Header dedupe never lets a generated `_N` suffix collide with any other final header, including one that is itself a later literal in the file: `"a,a,a_2"` — the literal `a_2` (3rd column) keeps its name; the duplicate `a` (2nd column) skips `a_2` (reserved for that literal) and becomes `a_3` instead. Every final header is guaranteed unique.
- **Malformed quoting**: a quote that opens right after a delimiter, closes, and is followed by more text before the next delimiter (e.g. `h,"b"c,d`) still makes Papa swallow the rest of the row (or, if it recurs, the rest of the file) into one field — that's inherent to quote-aware CSV parsing and isn't changed (the decision was to keep Papa rather than hand-roll different quote handling). What IS added: `ParseResult.quoteProblems: { row: number }[]` lists the first ~20 data-row numbers (1-based, as the user sees them) where Papa reported a quote-related error (`InvalidQuotes`/`MissingQuotes`/etc.). Papa reports every case where a bad quote swallows following rows; a `"` in the middle of an unquoted field raises no error because it parses correctly as literal text, so no banner is shown for it. The webview shows a dismissible warning banner above the table whenever `quoteProblems` is non-empty and quoting is on: "Quotes look malformed near row N — rows after it may be merged. [Treat quotes as plain text]". The button (and a "Quoted fields" toolbar checkbox, persisted per file as `ViewState.quotes`, default/fallback `true` for state saved before this field existed) sets `quotes: false` and re-parses: every `"` becomes literal text (Papa has no "off" switch for quoting, so this uses a `quoteChar` that can't occur in real text — a NUL sentinel, guarded against the rare case where the text already contains it). With quoting off, `"` also becomes a usable custom delimiter (see below) — the malformed-quote example above, re-parsed with `quotes: false`, correctly splits into 3 literal-quote-preserving fields.
- Blank lines (no characters at all) are skipped everywhere — via Papa's `skipEmptyLines: true` — both a trailing newline (no spurious empty row) and a fully blank line in the middle of the file. A line with only delimiters (e.g. `,,,`) is a real row of empty fields and is not skipped; this is a deliberate, documented choice, not an oversight.
- Delimiter: `ParseOptions.delimiter` — empty string or `undefined` means auto-detect via Papa's quote-aware guessing among `delimitersToGuess: [",", ";", "\t", "|"]`; a non-empty string (of any length, so multi-character delimiters like `||` are supported) forces that delimiter. `.tsv`/`.tab` files are given `"\t"` as the host's `defaultDelimiter`, used when no per-file separator is stored (see Custom separator, below). The old line-based `detectDelimiter` export and hand-written `tokenize` were removed along with the hand-written tokenizer; nothing needs a standalone delimiter guesser anymore since `parseCsv` returns the one it used.
- First row is header. Duplicate/empty header names get made unique (`name`, `name_2`; empty → `column_N`). Toggle "First row is header" in toolbar (persisted per file); when off, headers are `column_1..N`. Toggling it re-parses locally in the webview from the text already held in memory — no host round-trip.

### Custom separator
- Toolbar "Separator" dropdown: `Auto (<detected>)` (e.g. `Auto (;)`, with a tab rendered as the word "Tab"), `Comma ,`, `Semicolon ;`, `Tab`, `Pipe |`, and `Custom…`. Custom reveals a small text input (1–5 chars, applied on input after a 300ms debounce); the typed value is **not trimmed** (a single space or a tab is a valid 1-character delimiter someone might actually type here), only a truly empty input falls back to Auto. `"` is rejected with an inline error ("`"` is the quote character — turn off Quoted fields to use it") and never applied while quoting is on — Papa's `quoteChar` conflicts with it, and Papa also hardcodes `"` as an always-bad delimiter (`Papa.BAD_DELIMITERS`) regardless of `quoteChar`, so `parseCsv` works around that internally (substituting a delimiter Papa will accept before parsing) whenever `"` is requested with `quotes: false`. With quoting off, `"` **is** allowed as the custom delimiter.
- Persisted per file in `ViewState.delimiter` (`""` = auto). Values stored before this field existed lack it entirely — treated the same as `""`.
- Precedence when resolving what to actually parse with: the stored per-file choice, else the host's `defaultDelimiter` (tab for `.tsv`/`.tab`), else real auto-detection.
- Changing the separator re-parses locally from the held text, reconciles column visibility (new header names follow the default-N rule — a name that existed before, even coincidentally, keeps its prior visibility), resets to page 1, and posts `saveState`. Filter rules are left as-is, but no longer misbehave when stale: a rule pointing at a column that no longer exists is *ignored* (see Filtering, above), not applied as "matches nothing" — the fix that stops a single stale include rule from hiding the entire file applies here too, the same as after a header rename. Sort keys pointing at a missing column are unaffected either way (already silently skipped).

## Architecture
- `CustomReadonlyEditorProvider<CsvDocument>` (changed from v0.3's `CustomTextEditorProvider` — see "Why readonly" below), viewType `csvViewer.table`, priority `option` (text editor stays default). Selector `filenamePattern`s are `*.[cC][sS][vV]`, `*.[tT][sS][vV]`, `*.[tT][aA][bB]` — character classes so `DATA.CSV`, `Data.Tsv`, etc. match too (VS Code's plain `*.csv`-style pattern matching is case-sensitive; a bare lowercase pattern silently didn't match uppercase-extension files in "Open With…"). Menu `when` clauses use `resourceExtname =~ /^\.(csv|tsv|tab)$/i` (a case-insensitive regex) for the same reason — `resourceExtname` preserves on-disk casing and `==` is case-sensitive, so the old `resourceExtname == .csv || ...` clauses never showed "Open in CSV Viewer" for an uppercase-extension file's Explorer/editor-title/palette entries. Commands: `csvViewer.open` ("Open in CSV Viewer") available in explorer context menu, editor title bar (icon) for csv/tsv files, and command palette; `csvViewer.openAsText` from inside the viewer.
- `openCustomDocument(uri)` returns a minimal `CsvDocument { uri, dispose() {} }` — no I/O. `resolveCustomEditor(document, webviewPanel)` does the real work: reads the file with `vscode.workspace.fs.readFile(uri)` and decodes it with `new TextDecoder("utf-8", { fatal: false })` (BOM handling stays in `parseCsv`, unchanged). Reading through `workspace.fs` — instead of waiting for VS Code to hand the provider a synced `TextDocument`, which is what `CustomTextEditorProvider` required — is also why `capabilities.untrustedWorkspaces.supported` and `capabilities.virtualWorkspaces` can both be declared `true` in package.json: there's no arbitrary code execution, no writes, and reads go through the same virtual-filesystem-aware API a virtual workspace provides for any other extension.
- **Why readonly**: VS Code will not sync a text document to a `CustomTextEditorProvider` above a size ceiling of its own (~50 MB in 1.139.1) — `resolveCustomTextEditor` simply never ran for a file that big, no matter what this extension warned about. Switching to `CustomReadonlyEditorProvider` and reading bytes directly with `workspace.fs.readFile` bypasses that ceiling entirely (verified: 51 MB and 120 MB files now open and render, in ~2s and ~5s respectively in this environment — see the integration suite's `largeFiles.itest.ts` for current numbers). The trade-off, and it's a deliberate one: **unsaved edits in a side-by-side text editor are no longer reflected in the viewer.** The old `CustomTextEditorProvider` design watched `onDidChangeTextDocument`, which fired on every in-memory edit whether saved or not; a readonly provider never gets that document at all, so the viewer can only ever reflect what's actually on disk. Users who want to see an edit live must save it first (Ctrl/Cmd+S) — same as any other file-backed preview.
- **Size limits**: above 50 MB (checked via `vscode.workspace.fs.stat(uri).size` — an exact byte count, not the `document.getText().length` estimate v0.3 used, since there's no `TextDocument` to estimate from any more) shows a "may be slow" warning and still loads, same threshold as before. A new, harder line: above **512 MB**, an error is shown and the file is not read or loaded at all, so an enormous file can't be dragged into memory and wedge the extension host. (Measured: 513 MB is rejected via `stat()` alone, no `readFile`, in a few seconds.)
- **Live reload**: a `vscode.FileSystemWatcher` on exactly the open file — `new vscode.RelativePattern(vscode.Uri.joinPath(uri, ".."), basename)` — not a workspace-wide watcher, so it works for a file outside any open workspace folder too (this is also why virtual/untrusted workspace support is safe: the read path is identical everywhere). On change, debounced 300ms per panel (so a burst of rapid saves — or a rewrite that lands in several small writes — coalesces into one reload) and cancelled on dispose, the file is re-read and a fresh `load` is posted, same as v0.3's re-send. On delete, a **non-modal warning** ("File was deleted — showing last loaded contents") is shown and nothing is re-read — the webview already holds the last successfully parsed data in memory and keeps showing it. Everything (watcher, its `onDidChange`/`onDidCreate`/`onDidDelete` subscriptions, the debounce timer) is disposed together in the panel's `onDidDispose`, mirroring how v0.3 disposed its `onDidChangeTextDocument` subscription.
- **Rename**: a global `vscode.workspace.onDidRenameFiles` listener (registered once in `activate()`, not per panel) moves the renamed file's `workspaceState` entry from the old uri's key to the new one, and deletes the old key — both for a plain file rename and, by also matching any key nested under the old prefix, for a folder rename that carries files underneath it. A viewer left open on the renamed-away file keeps working: since its `FileSystemWatcher` still targets the *old* path, VS Code reports that as a delete (see above) — the viewer shows the "file was deleted" warning and keeps its last-loaded contents rather than trying (and failing) to follow the rename to the new path. Opening the file at its *new* path picks up the migrated state, so it doesn't go through fresh first-open reconciliation the way a genuinely new file would.
- **Parsing happens in the webview, not the host** (unchanged from v0.3, for performance — see below). The host never calls `parseCsv`; it only reads the file's bytes and ships the decoded text once per load/reload. Webview → host messages: `ready`, `saveState(state)`, `openAsText`. Host → webview: `load({ fileKey, text, state, defaultTableColumns, defaultDelimiter })` — `text` is the whole file's decoded text (not `headers`/`rows`), and `defaultDelimiter` is `"\t"` for `.tsv`/`.tab`, else `""`. This message shape is unchanged from v0.3 — only how the host obtains `text` changed.
- **Parsing, filtering, and sorting run in a dedicated Web Worker (`src/webview/worker.ts`, bundled to `out/webview/worker.js`), never on the main/UI thread.** A catastrophic regex (e.g. `(a+)+$`) or a large filter/sort used to block the whole webview outright (measured at 200k rows: 2.6s to first render, 1.3s to add a filter). The worker owns the full parsed dataset; the main thread only ever holds small summaries (headers, `detectedDelimiter`, `quoteProblems`, total/filtered row counts) plus the *current page's* rows, with full, untruncated cell values (truncation is render-only — see "Huge cells", below). It never posts the full rows array back.
  - Protocol (`src/webview/workerProtocol.ts`): `init` (once per load/re-parse: the whole text + parse options) → `initResult` (headers/detectedDelimiter/quoteProblems/totalRows); `query` (`quickSearch`/`filterRules`/`sortKeys`, whenever any changes) → `queryStarted` (posted right before `applyFilters` begins) → `filterDone` (posted right after `applyFilters`, before sorting) → `queryResult` (filtered count only — the worker caches the filtered+sorted row order, as row ids); `page` (page/pageSize) → `pageResult` (that page's rows). Paging alone (Next/Prev/page-size change) only ever sends `page` — it never re-filters/re-sorts. Every request carries a monotonically increasing request id, echoed back unchanged, so the main thread can recognize and drop a stale response (e.g. an in-flight quick-search query superseded by a newer one before it answers) rather than ever rendering it.
  - **No-op query skip**: `runQuery()` (`src/webview/main.ts`) computes a canonical key from quickSearch, sort keys, and only the *active* filter rules (`enabled && isRuleActive(...) && !timedOut`, reduced to their semantic fields) — see `buildQueryKey`. If that key is unchanged from the last query actually sent, no `query` message goes out at all; only the desired page is (re-)fetched from the worker's already-correct cached view. This is what makes an intermediate filter-rule edit — adding a still-empty rule, picking its column or operator before it has a value — free: none of those change which rules are *active*, so the key doesn't change either. `requery()` is shared by quick search, every filter-rule control, and sort, always resetting to page 1 — filter-rule controls (column/operator/value/case/enabled/mode, add/remove) additionally share one 150ms debounce (`FILTER_RULE_DEBOUNCE_MS`) so a multi-field edit (column, then operator, then value) coalesces into the single query that reflects its *final* state, on top of the no-op skip itself.
  - **Sort-key cache** (`worker.ts`): a column's resolved sort key (empty/numeric/text kind, plus a collator-ranked text index — `src/core/sort.ts`'s `ResolvedCellSortKey`, via the newly-exported `buildColumnSortKeys`) is computed once, over the *entire* dataset, the first time that column is used as a sort key, and reused for every later query until the next `init` invalidates it. Re-sorting a filtered subset after that (`sortRowIdsByCachedKeys`, also exported from `src/core/sort.ts`) is then just stable integer/rank comparisons over however many rows survived filtering — never re-deriving each cell's kind or re-running the collator over the column's distinct values again. Sorting a subset by ranks computed over the *full* dataset produces identical relative order to computing them over just that subset (a value's collator-equality with another is independent of what else is in the ranked set) — this equivalence, and that the cached-key path orders exactly like plain `sortRows`, is covered by unit tests including a fast-check property in `src/test/sort.test.ts`. `sortRows` itself is now implemented in terms of these two functions (so it can't silently drift from them) and its own behavior/tests are unchanged.
  - **Regex timeout**: a `query` containing an enabled, syntactically-valid regex rule is tracked as "at risk"; the actual 2000ms watchdog for that specific request only starts once the *worker* confirms it has begun running (`queryStarted`), and is disarmed the moment filtering finishes (`filterDone`), before any sorting happens. This — not arming at send time — is what a request merely queued behind an earlier one (or paired with a slow sort afterward) needs: it's never penalized for time spent waiting its turn in the worker's single-threaded mailbox, or for a slow sort that isn't the regex's own doing. If the watchdog does fire (presumed stuck in catastrophic backtracking), the stuck worker is `terminate()`d, a fresh one is created, the offending rule(s) are added to a webview-only `timedOutRuleIds` set and excluded from every future query the same way an invalid regex is excluded (`isRuleActive`/`applyFilters` themselves are untouched — the exclusion happens by never sending that rule to the worker), the fresh worker is re-initialized with the same text/options, and the query re-runs without the disabled rule(s). The Filters panel shows "Regex too slow — rule disabled"; editing that rule's value clears the mark immediately (before the next query even answers) and gives it a fresh chance. A page navigation requested while a query is in flight (including during regex-timeout recovery) is queued (`pendingPageAfterQuery`) and applied once the in-flight query settles, rather than dropped — the main thread is never blocked by the worker regardless, so the UI (including pager buttons) stays responsive throughout.
  - **"Working…" indicator**: a subtle status-bar-adjacent label (`#working-indicator`), shown only once an interactive request (filter/sort/search/page change) has been in flight longer than 150ms, and hidden the moment the corresponding render completes. Never shown during the initial `load` (which already shows "Loading…").
  - **CSP / loading under a webview**: a webview can't load a `vscode-resource:` URI directly as a `Worker` script. `buildHtml` (`extension.ts`) passes the worker script's webview URI via a `data-worker-src` attribute on `#app`; the webview fetches that URI's *text* (allowed by the CSP's `connect-src ${webview.cspSource}`) and loads it from a `Blob` URL instead (allowed by `worker-src blob:`). The Playwright harness (`src/test/webview-e2e/harness.ts`) exercises the identical code path via a routed fake URL rather than skipping it, and the integration suite (`npm run test:integration`, real VS Code) is what actually proves the Blob-URL approach works under the real webview CSP — the Playwright harness alone doesn't prove that.
- The webview's `onLoad` handler shows "Loading…" in the status bar and yields one frame (`requestAnimationFrame`/`setTimeout 0`) before creating/using the worker, so the placeholder actually paints before a large parse starts. It reconciles column visibility itself once the worker's `initResult` answers (the host no longer does — `defaultVisibility`/`reconcileVisibility` are webview-only) and only posts `saveState` back if reconciliation actually changed the stored visibility map, so a plain reopen of an already-settled file doesn't write on every open. The webview holds onto `text` in its in-memory state so the "first row is header" toggle and separator changes (see Custom separator, above) can re-send it to the worker (a fresh `init`) without another host round-trip.
- Filtering/sorting/pagination logic itself is still the same pure functions in `src/core/` (unchanged behavior — only *where* they run moved, into the worker); column visibility and expand/collapse stay fully on the main thread and never touch the worker, since they only affect which columns/fields render from the already-fetched current page, not which rows match or their order.
- Webview: vanilla TypeScript + CSS, bundled with esbuild to `out/webview/main.js` (main thread) and `out/webview/worker.js` (worker, same esbuild settings, its own entry point). Strict CSP with nonce, `worker-src blob:`, `connect-src ${webview.cspSource}`; `localResourceRoots` limited to `out/webview` + `media`. Use VS Code theme CSS variables (`--vscode-*`) only — must look right in light, dark, high-contrast.
- **Huge cells**: table cells render at most 500 characters (+ "…") — a 15 MB single-line cell used to be rendered in full and trip VS Code's unresponsive-webview watchdog. The detail (expanded row) view renders at most 10,000 characters (+ "…") plus a "Show all (N characters)" button that expands the field in place; above 1 MB the button's `title` warns that showing it in full may be slow. Truncation (`src/core/truncate.ts`, pure, render-only) never touches the underlying data: the worker always returns full cell values, so right-click quick-add (which needs the real value to build an `equals` rule) is unaffected regardless of how a cell is currently truncated on screen.
- Performance: must stay responsive for 100k rows × 30 cols — and, since parsing/filtering/sorting moved to a worker, must also stay *interactive* (never freeze the page) even on a pathological regex or 200k+ rows. Don't render all rows: pagination renders only the current page's rows (see Pagination above) instead of chunked/infinite-scroll rendering. Sticky header row. Targets at 200k rows × 30 cols, measured in Playwright (`src/test/webview-e2e/stress/scale.spec.ts`, ×2 under CI): first render under 2000ms, adding/changing a filter rule under 500ms end to end, sorting under 500ms. Quick-search per-keystroke latency stays under 150ms at 50k rows (the keystroke's own DOM event is unaffected by the debounce; only the resulting re-filter is delayed/off-thread).

## Project layout / conventions (mirror ~/projects/markdown-collab-plugin)
- TypeScript strict, `tsconfig.json` (extension, commonjs, ES2022), separate `tsconfig.webview.json` (DOM lib, noEmit type-check — covers `src/webview/**` including `worker.ts`, plus `src/core/**`).
- esbuild bundles: `out/extension.js` (platform node, external vscode — no longer imports `csvParse`/papaparse now that parsing is webview-only), `out/webview/main.js` (iife, browser), `out/webview/worker.js` (iife, browser, its own entry point — `bundle:worker`) — both webview bundles bundle `papaparse`, self-contained so `vsce package --no-dependencies` still works.
- Pure logic in `src/core/` (`csvParse.ts`, `filter.ts`, `sort.ts`, `columns.ts`, `paging.ts`, `truncate.ts`, `types.ts`) — no DOM, no vscode imports. `csvParse.ts` depends on `papaparse` (a runtime dependency; `@types/papaparse` is dev-only) but is otherwise still pure/no-DOM, so it unit-tests in node and bundles into both the main-thread and worker webview bundles unchanged.
- Unit tests: vitest, `src/test/**/*.test.ts`.
- Webview e2e: Playwright (`@playwright/test`, Chromium at `/opt/pw-browsers` via `PLAYWRIGHT_BROWSERS_PATH` if set; locally `npx playwright install chromium` is allowed only if no browser found). Harness loads the built `out/webview/main.js` into a page with a stubbed `acquireVsCodeApi`, routes a fake worker-script URL to the built `out/webview/worker.js` (so the same Blob-URL loading path used in production is exercised here too), posts a `load` message, then drives the UI. `bootAndLoad(page, { headers, rows, fileKey, state, defaultTableColumns, defaultDelimiter? })` keeps the convenient headers/rows fixture shape specs have always used, serializing to CSV `text` under the hood via `Papa.unparse` (matching the real `load` message shape); `bootAndLoadText` takes raw text directly for specs exercising parsing itself. A multi-hundred-thousand-row fixture's text is generated *inside* the page (not passed as a Playwright `evaluate` argument) in perf-sensitive specs, since shipping tens of MB through Playwright's own Node↔browser argument serialization can itself cost seconds — a test-harness artifact that would otherwise dominate a timing assertion and measure Playwright's plumbing instead of the webview's own pipeline.
- Scripts: `compile` (now also runs `bundle:worker`), `watch`, `test`, `test:webview`, `test:integration` (real VS Code via `@vscode/test-electron`, `src/test/integration`; separate `tsconfig.integration.json` — this is what actually proves the worker loads under the real webview CSP), `package` (`vsce package --no-dependencies` producing a `.vsix`).
- README with features, screenshots placeholder, install-from-vsix instructions for VS Code and Cursor.
- `.vscodeignore` so the vsix only ships `out/`, `media/`, `package.json`, README, LICENSE (MIT), CHANGELOG. `out/webview/worker.js` ships alongside `main.js` (only `out/core/**` and `out/test/**` — tsc's per-file emit, never loaded at runtime — are excluded).
