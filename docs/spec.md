# CSV Viewer — VS Code extension spec

Table viewer and cell editor for CSV/TSV files: reads files of any size the editor can hold, and (since 0.8.0) lets the user change existing cell values and save them back with a minimal, byte-exact diff — see "8. Cell editing" and the Architecture section's document model. Works in VS Code and its forks (Cursor, Windsurf) — target Open VSX + VS Code Marketplace, `engines.vscode: ^1.80.0`.

## Core features

### Toolbar, banners, and status

One row: a quick-search box, then three badge buttons that each open a popover —
**Columns n/N**, **Filters** (shows **Filters • N** once N ≥ 1), **Sort** (likewise
**Sort • N**) — then icon buttons: an expand/collapse-all toggle, **File format**
(gear icon), and **Open as Text**. The row's height never changes as badges or
popovers open or their counts change.

Directly under the toolbar sits a 2px indeterminate progress bar
(`#working-indicator`, using `--vscode-progressBar-background`), shown only once
an interactive request (filter/sort/search/page change) has been in flight longer
than 150ms, with `aria-busy="true"` set on the table meanwhile — this replaces the
old "Working…" text; it's never shown during the initial `load` (which shows
"Loading…" in the status region instead). Below that, in order, each hidden unless
relevant: a file-deleted banner, a malformed-quote warning banner, a one-time
row-details hint banner (see "Banners, hints, and context menu" below), and a slim **"Filtered: X
of Y rows"** row with **Clear Search** / **Turn Off Filters** buttons shown while a
search or an active filter rule is in play (regardless of whether it actually
reduced the row count — the pager's own "(filtered from N)" suffix is what's gated
on an actual reduction, see Pagination below).

`#status-bar` is a visually-hidden `role="status"` live region carrying "Showing X
of Y rows" for assistive tech only; sighted users read the row count from the pager
bar instead (there is no visible "Showing X of Y rows" line anymore).

### 1. Column visibility: table vs detail
- Each column is either **shown in table** or **detail-only**.
- Every table row has an expand chevron (a "twisty" button, excluded from the Tab order — see Keyboard, below) and clicking the row toggles it (clicking to select text, or finishing a drag-selection, does not). Expanded row shows a detail panel below it:
  - **detail-only columns** first, as a label/value list; then, if any table-visible column's cell is currently clipped (ellipsis), contains a line break, or is longer than `TABLE_CELL_MAX_CHARS` (500 — such a cell is always drawn truncated, and the third rule makes the group deterministic rather than layout-dependent, which cell editing relies on: see "8. Cell editing"), a second **"Also in table"** group listing those — so a long value hiding in a visible column is still reachable. If nothing is hidden and nothing is clipped, the panel falls back to showing every column.
  - Each field's value: an em dash ("—") when empty; a value that parses as a JSON object/array (`src/core/json.ts`) is pretty-printed with a **Raw / Formatted** toggle (the original text is re-indented token by token by `formatJsonText`, never round-tripped through `JSON.parse`/`JSON.stringify`, so big integers, number formatting and duplicate keys are shown exactly as written); clamped to 6 lines with a **More** / **Less** link; capped at 10,000 characters with a **Show all (N characters)** / **Show less** link (above 1 MB its title warns that showing it in full may be slow); a per-field **copy** button (a codicon that briefly swaps to a checkmark) always copies the full raw value, never the pretty-printed or truncated display text.
  - **Markdown in row details** (never in table cells, which stay raw and single-line). A non-empty value that is not JSON and is at most 100,000 characters (`MARKDOWN_MAX_CHARS`) is *Markdown-capable*; JSON values keep the Raw / Formatted behaviour above and are never Markdown, and longer values are always raw with no Markdown link. A column is in Markdown mode when the user chose so explicitly (`ViewState.markdownColumns`, below) or, with no explicit choice, when it is **auto-Markdown** (profile `markdownShare >= 0.1`, below). In Markdown mode every Markdown-capable value of that column is rendered by `renderMarkdown` (`src/core/markdownRender.ts`) into a `.detail-value-md` block and the toggle link (same slot and `link-btn format-toggle-btn` class as the JSON toggle, before More/Less) reads **Raw**. In Raw mode the value is shown as before, and a **Markdown** link appears only when the value is Markdown-capable and (contains a line break, or is longer than 60 characters, or `looksLikeMarkdown(value)`), so short plain fields don't all grow a link.
    - Clicking **Raw** / **Markdown** flips the explicit choice for the whole **column**: `setColumnMarkdown` (`main.ts`) re-populates every visible detail field of that column in every expanded row from the values already on the page (no worker round-trip; rows stay expanded; other columns' fields keep their More/Less/Show all state), moves focus back to the clicked field's toggle, and posts `saveState`. The clicked field keeps a **Markdown** link even if it is short and plain (it would otherwise lose the only control that flips it back).
    - Clamp: rendered Markdown is clamped to six lines by a max-height (`.detail-value-md-clamped`, `calc(6 * 1.5em)` — `-webkit-line-clamp` does not work on block content) with the same More / Less link; overflow is measured against the unclamped height, as for raw text. The 10,000-character cap applies to the Markdown source: the rendered text comes from `truncateForDetail` of the value, with the same **Show all (N characters)** / **Show less** link (Show all renders the full value, at most 100,000 characters by definition).
    - The per-field copy button, **Copy Value** and the quick-filter items always use the full raw value, never rendered text. A rendered link is just an `<a>` inside the detail row (a sibling of the data row, not a child), so clicking it never toggles or collapses a row.
    - **Safety.** `renderMarkdown` is the only place `innerHTML` is fed from cell content. markdown-it runs with `html: false` (raw HTML in a cell is escaped and shown as text), `linkify: false`, `typographer: false`, `breaks: true` (a single newline is a line break, so plain multi-line text reads as it did before); GFM tables and strikethrough are on. Only `http:`, `https:` and `mailto:` hrefs become `<a>` (with `rel="noopener noreferrer"` and `title` = the URL); every other link (relative, `#anchor`, `javascript:`, `data:`, `file:`, …) renders as its plain text. Images are never loaded: `![alt](src)` renders as a link (same href rules) labelled with the alt text, or the URL when the alt is empty, and no `<img>` is ever produced, so the CSP's `img-src` is never exercised by cell content. Tables are wrapped in a scrolling `.md-table-wrap`; code blocks scroll inside themselves.
    - **Styles** (`main.css`, `--vscode-*` variables only, light/dark/high contrast): compact headings (h1 1.3em, h2 1.15em, h3+ 1em, weight 600), ~0.6em paragraph and list spacing, links in `--vscode-textLink-foreground`, inline code and code blocks on `--vscode-textCodeBlock-background` (neutral rgba fallback) in the editor monospace font, a blockquote with a left rule in the description colour, tables auto-width with 1px `--vscode-panel-border` cell borders. The page-level element rules (`th, td` nowrap/ellipsis/max-width/bottom border, sticky `thead`, `th` box-shadow, `table { width: 100% }`) match a table inside a detail value too, so `.detail-value-md` overrides each of them explicitly; the detail row's own accent-border/overflow rule is written `tr.detail-row > td` (child combinator) so it styles only the row's colSpan cell and never nested cells.
  - The detail block is pinned (`position: sticky; left: 0`) and sized to the visible width of the table's scroll viewport (kept in sync via `ResizeObserver`), so it doesn't scroll sideways with a wide table and wraps prose within what's actually visible rather than the table's full scrolled width.
- The **Columns n/N** toolbar button opens a popover: a legend ("Unchecked columns appear in row details"), a search box to filter the list, **All in Table** / **All in Details** buttons, and one checkbox per column (checked = shown in table).
- Default visibility when a file is first opened is **content-based**, not positional. The worker samples the first 200 data rows per column (`profileColumns`, `src/core/columns.ts`) and computes a profile per column: median trimmed length, the share of non-empty sampled values containing a line break, the share that parse as a JSON object/array, the share that parse as a number (via the shared `parseNumber`), and `markdownShare` — the share for which `looksLikeMarkdown` (`src/core/markdownDetect.ts`) is true. A column is **auto-Markdown** when `markdownShare >= 0.1` (`isAutoMarkdownColumn`); that never affects the table/detail split. A column is "short" — and defaults into the table — unless its median length exceeds 60 characters, at least 10% of its sampled values are multi-line, or at least 50% parse as a JSON object/array. Columns are walked in file order and put in the table while short, against a budget of `csvViewer.defaultTableColumns` (default 8) minus however many columns already have a stored visibility choice and are visible — so the setting is a **cap** on the table's total column count, not a literal "first N" rule. A column with an explicit stored choice always keeps it and is never reconsidered by the profile. If a completely fresh file (no stored choice for any current header) ends up with nothing visible and the cap is ≥ 1, the first column is forced visible so the table is never left empty.
- Persist column visibility per file (keyed by file URI) in `workspaceState`. If the header row changes, the map is **merged**, not replaced: every previously-known column's setting is kept (even for a name the *current* header list no longer has), and only the current header list decides what's actually shown/hidden right now. This is what makes a setting survive an intermediate reconciliation against a *different* header set — e.g. toggling "First row is header" off (synthesizing `column_1..N` headers) and back on — instead of being silently dropped and reset to the default rule. New columns follow the default rule above.
- `ColumnVisibilityMap` is safe for any header name, including `__proto__`, `constructor`, `toString`, and `hasOwnProperty` — `src/core/columns.ts` writes every entry via `Object.defineProperty` (which bypasses `Object.prototype`'s `__proto__` accessor, whose setter otherwise silently no-ops for a non-object value) and reads only via `Object.prototype.hasOwnProperty.call` plus a `getVisibility` helper, never a bare `map[header]`. Already-persisted plain-object maps keep working: `JSON.parse` (the shape `workspaceState` round-trips through) creates a genuine own `"__proto__"` property per the JSON spec, unlike a runtime `obj["__proto__"] = x` bracket assignment.
- **Markdown detection and state.** `looksLikeMarkdown(value)` (`src/core/markdownDetect.ts`, pure, no dependencies — the worker bundle imports it) is never true for a JSON object/array (see `json.ts`). *Strong* signals, any one of which suffices: an ATX heading line (`/^#{1,6} \S/m`), a fenced code block (a line starting with ``` or ~~~), a Markdown link `[text](http…|mailto:…)`, a table delimiter row (`| --- | --- |` style). *Weak* signals, at least two **different kinds** needed: `**bold**`/`__bold__`, two or more bullet-list lines (`- `, `* `, `+ `), two or more ordered-list lines (`1. `), a blockquote line (`> x`), inline code (`` `x` ``). Prose with a stray `*`, `#` or `1.` stays plain. Only the first 100,000 characters of a value are scanned. `ViewState.markdownColumns: { [column]: boolean }` holds only the user's explicit choices (`true` = Markdown, `false` = Raw); the effective mode of a column is the explicit choice if there is one, else auto-Markdown from the profile. State saved by older versions lacks it and is normalized to `{}` (`normalizeColumnFlags`, in both `extension.ts`'s stored-state load and the webview's `onLoad`); `createDefaultViewState` and the e2e harness's `defaultViewState` return `{}`. Entries for columns not in the current header list are kept (the same merge philosophy as visibility). The map is `__proto__`/`constructor`-safe exactly like `columnVisibility`: `columns.ts` generalizes the safe accessors as `getColumnFlag`/`setColumnFlag`/`hasColumnFlag` (`getVisibility` & co. are aliases), never `map[header]`. A saved choice reaches the webview only through the host's `load` (a same-fileKey live reload keeps the choice because the host sends back the state it saved).
- Columns the worker's profile classifies as numeric (`isNumericColumn`: at least 90% of a column's non-empty sampled values parse via the shared `parseNumber`) are right-aligned in the table body (`.numeric-cell`).
- The single expand/collapse-all toolbar icon button toggles the *current page's* rows only — see Pagination, below.

### 2. Filtering (include + exclude)
- Toolbar: global quick search box (case-insensitive substring over all columns, debounced ~150ms). "Case-insensitive" here means the shared `foldCase` (below), not plain `toLowerCase()`.
- **Filters** toolbar button opens a panel: "Rows must match all rules.", one row per rule, an **Add Rule** button, and — only while the rule list is empty — a tip ("Tip: right-click any cell to filter by its value."). Each rule reads as a sentence: `[enabled checkbox] [Keep ▾ / Hide ▾] rows where [column ▾] [condition ▾] [value] [Aa] [✕]`.
  - the **Keep** / **Hide** select is the mode toggle (the stored field is still `mode: "include" | "exclude"`; exclude/"Hide" drops a row that matches)
  - column: any single column, or "Any column"
  - condition: `contains`, `equals`, `is any of`, `starts with`, `ends with`, `regex`, `is empty`, `> (number)`, `< (number)`, `>= (number)`, `<= (number)` (numeric operators compare via the shared `parseNumber`, below; a rule fails if the cell isn't numeric; `is any of` is the "filter by values" operator, described under "Filter by values", below)
  - value (hidden for `is empty` and `is any of`)
  - "Aa" case-sensitive toggle (default off; hidden for `is any of`, which ignores it)
  - a remove (✕) button
- All enabled, **active** rules combine with AND (include/"Keep" rules must all match; any matching exclude/"Hide" rule drops the row). A rule is **active** exactly when `isRuleActive(rule, headers)` (`src/core/filter.ts`) says so — the single helper `applyFilters`, the filter panel UI, and the **Filters • N** toolbar badge all use, so they always agree. A rule row shows one of three states, in order of precedence:
  - **Regex timed out** (see the regex watchdog, below) → strong error styling (an error icon, red outline) with "Skipped: pattern took over 2 s. Edit it to retry." — cleared the instant the rule's value is edited.
  - **Invalid regex** → same strong styling, "Skipped: invalid regex (‹the JS engine's own error message›)".
  - **Column no longer exists** (e.g. after a header rename or a separator change that changes the column count) → same strong styling, `Skipped: column "‹name›" isn't in this file`; the missing column still appears in the column select, as a disabled `‹name› (missing)` option, so the user can see which one. Any of these three means the rule has *no effect*, not "matches nothing" — an ignored include/"Keep" rule leaves every row as-is; treating a missing column as "matches nothing" (the pre-fix behavior) meant one stale rule could silently hide the entire file.
  - **Empty value** on any operator except `is empty` (which takes no value) and `is any of` (which takes a list, below) → a softer hint style (dashed outline), "Enter a value" — for the same reason an empty value's incidental per-operator behavior isn't a well-defined "the user meant this," so the rule does nothing until a value is entered.
  - **`is any of`** with "Any column" → the same soft hint, "Choose a column"; with a specific column but no values → "Choose values". (A missing column keeps the strong "Skipped: column … isn't in this file" error above.)
- Case-insensitive matching (every string operator above, and quick search) uses a shared `foldCase(s)` (`src/core/caseFold.ts`): `toLowerCase()`, then drop the combining dot above (U+0307) that follows an "i" (so Turkish `İ` folds to plain `i`, not `i` + a stray combining mark), then fold `ß` → `ss` (so `STRASSE` matches `straße`). No accent-stripping beyond those two rules.
- Numeric operators use a shared `parseNumber(s)` (`src/core/number.ts`, also used by sort — see below): trim, then accept only `/^[+-]?(\d+(\.\d*)?|\.\d+)([eE][+-]?\d+)?$/`. This is stricter than plain `Number()`: it rejects hex (`0x10`), `Infinity`/`NaN` text, thousands separators (`1,000`), and currency/percent symbols (`$5`, `5%`); `1e3` (scientific notation) still parses.
- Quick-add via context menu: right-click any table cell or detail field value → **Copy Value**, then (below a divider) **Show only rows where ‹column› = "‹value›"** / **Hide rows where ‹column› = "‹value›"** (creates an `equals` rule with the full, untruncated value — only the menu item's own label is shortened to 40 characters), then (below another divider) **Copy Row as CSV** / **Copy Row as JSON** (see "Banners, hints, and context menu", below). Adding a quick filter opens the Filters panel and re-queries immediately. A third item, **Filter ‹column› by Values…** (see "Filter by values", below), sits right after these two.
- A `#status-bar` live region (visually hidden) carries "Showing X of Y rows" for assistive tech; the pager bar's row range (see Pagination) is what's visible on screen.
- Persist filter rules per file alongside column settings.

#### Filter by values (`is any of`)
A Google-Sheets-style way to keep or hide several exact values of one column, reachable from three places that all open the same **values picker**: a funnel button in every sortable column header, the Filters panel's `is any of` condition, and the cell context menu's **Filter ‹column› by Values…**.

- **Data model.** `FilterOperator` gains `"in"`; `FilterRule` gains an optional `values?: string[]` (used only by `in`; state saved by older versions lacks it and is treated as `[]`). `value` and `caseSensitive` are ignored by `in` but stay on the rule untouched, so switching the condition away and back loses nothing. A cell matches `in` when its raw string is **exactly** equal (case-sensitive, no trimming) to one of `values`; `""` in `values` matches empty cells (including a ragged row's missing cell). `compileRule` (`src/core/filter.ts`) builds a `Set` from `values` once per rule, never per row. Mode works as for every operator: include/"Keep" keeps matching rows, exclude/"Hide" drops them. `isRuleActive` is true for `in` only when `column !== null`, the column exists in the file, and `values` is a non-empty array — so "Any column" and an empty list are inactive (ignored, not "matches nothing"), and the "empty `value` ⇒ inactive" check doesn't apply to it.
- **Distinct values** come from `distinctValues(rows, columnIndex, caps?)` (`src/core/distinct.ts`, pure): `{ values: { value, count }[], truncated }`, counted over **all** parsed rows of the file — never the currently filtered view, so a value hidden by another filter or the quick search can still be ticked (a missing cell counts as `""`). At most 10,000 distinct values and 2,000,000 total characters across the collected values; once either cap is hit no new distinct value is added (`truncated: true`) but rows holding an already-collected value keep being counted, so every reported count is exact. Order is deterministic: `""` first, then numeric values (shared `parseNumber`) ascending by number, then text via `Intl.Collator(undefined, { numeric: true, sensitivity: "base" })`, with raw-string comparison as the tie-break. Keyed by a `Map`, so `__proto__`/`constructor` are ordinary values.
- **Header funnel.** Every sortable column `<th>` holds a `.th-inner` flex row: the sort button (`.col-header-btn`, takes the remaining width; a long name ellipsizes inside it) then a funnel button `.col-filter-btn` (codicon `filter`, never shrinks or clips) with `aria-label` and `title` `Filter ‹column› by values`, `aria-haspopup="dialog"` and `aria-expanded`. Clicking it opens the picker and never sorts; the header row's height is unchanged. It is always visible but dim (opacity ~0.55), full strength on hover, keyboard focus, while its picker is open, when active, and always in high-contrast themes. **Active** (class `active`, codicon `filter-filled`, `--vscode-textLink-foreground`) exactly when some rule with `operator === "in"` on that column is enabled and `isRuleActive`; it is recomputed in place by `renderFiltersButton` (the Filters badge's renderer), so it follows every path that changes a rule — picker OK, panel edits, the enable checkbox, remove, Turn Off Filters, reload — without waiting for a worker round-trip.
- **The picker** is one shared element, `#values-popover` (`role="dialog"`, `aria-label` = its title), built with `textContent` only (a value such as `<img src=x onerror=…>` renders as text). Top to bottom:
  - title: `Filter “‹column›” by values` for a Keep rule (or no rule yet), `Hide rows where “‹column›” is any of` for a Hide rule;
  - a search box (`type="search"`, `Search values…`, focused on open): case-insensitive substring over the value text via `foldCase`; `(Blanks)` matches the label text;
  - `Select all N` and `Clear` link-buttons — acting only on the values **currently shown** (those matching the search), N being how many that is — and right-aligned `X of Y selected` (Y = every value in the list, X = ticked);
  - a scrollable list (max-height ~220px), one `<label>` per value: checkbox, the value, and its row count right-aligned; `""` is `(Blanks)` in italics/description colour; a value over 80 characters is cut with `…` for display (the full text, up to 500 characters, is its tooltip). At most 500 rows are rendered; if more match, `Showing the first 500 of N. Search to narrow.` If the list was truncated by a cap: `This column has more than 10,000 distinct values; only the first 10,000 are listed.` While the worker answers: `Loading values…`; a search that matches nothing: `No values match`;
  - `Cancel` and a primary `OK`, disabled while nothing is ticked (and while loading).
- **Initial ticks.** Bound to an existing rule → that rule's `values`; a rule value the list lacks is still listed first, ticked, with count 0, so it can be unticked. No rule yet → everything ticked. A funnel (or the context menu item) binds to the **first** rule in `filterRules` with `operator === "in"` and that column — either mode, enabled or not; none → OK creates a new include rule.
- **OK** applies; nothing changes in the table before it. Cancel, Escape, or an outside click discards. Enter in the search box or on a checkbox is OK (when enabled); on a button it keeps its own meaning. For a Keep rule, if the list isn't truncated and every listed value is ticked, the rule is removed (or simply not created) — "everything" isn't a filter. Otherwise the rule is created/updated as `{ column, operator: "in", values: <ticked values, in list order>, mode, enabled: true }` (a new rule is `mode: "include"`, `value: ""`, `caseSensitive: false`). A Hide rule is never removed this way. Then the Filters panel, badge and funnels re-render, `requery()` runs immediately (not debounced), and `saveState` is posted. Focus returns to the control the picker came from (re-found by column / rule id, since the header and panel rows are rebuilt by renders).
- **Opening and closing.** Opened from a funnel or the context menu it behaves like the other popovers: it closes any open popover first, is anchored under the funnel with the same clamp/flip logic (re-clamped on window resize), and Escape returns focus to that funnel (looked up by column, as the header row is rebuilt on render). From the Filters panel the panel **stays open** underneath: clicks inside the picker don't close the panel, a click elsewhere in the panel just cancels the picker, Escape closes only the picker and returns focus to the rule's values button, and OK leaves the panel open with the rule row updated. A new `load` or re-parse (separator, header-row or quote change) while the picker is open closes it, discarding edits; regex-timeout recovery (same text, fresh worker) does not — the pending request is re-sent (see Architecture).
- **Filters panel.** `is any of` replaces the value input and the `Aa` toggle with a `.values-btn` (`aria-haspopup="dialog"`): a summary of the chosen values joined by `, ` (`""` shown as `(Blanks)`), cut to ~30 characters with `…`, then a muted `(N)` and a chevron; with no values, `Choose values…`. It is disabled while the column is "Any column". Clicking it opens the picker for that rule, anchored under the button. Changing the rule's column clears its `values` (they belonged to the old column's list).

### 3. Sort
- Click a table header: cycles asc → desc → none (`aria-sort="ascending"|"descending"|"none"` on the `<th>`). Shift+click adds/advances a secondary sort key (multi-sort); the header shows a direction arrow and, once there's more than one key, a priority number badge.
- The **Sort** / **Sort • N** toolbar button opens a popover: one row per current key (priority number, column name, a direction-toggle icon button, a remove (✕) button), an **"Add sort column…"** select listing every column *not already a key* — including detail-only columns, since they have no header to click — and a **Clear Sort** button once at least one key exists. Adding a key via the select, or clicking a header, mutate the same `sortKeys` list and both stay in sync automatically.
- Type-aware comparison, computed as one canonical sort key per cell per sort column, up front (not re-derived per pairwise comparison — see below): a value is **empty** (always sorts last, in both directions), **numeric** (parses via the shared `parseNumber`, above), or **text** (everything else, compared via a shared `Intl.Collator(undefined, { numeric: true, sensitivity: "base" })`). Within a kind, numeric compares by value and text by the collator, both direction-adjusted; across kinds, numeric sorts before text in ascending order and after text in descending order (so direction still flips the *relative* ordering of numeric vs. text, same as it flips numeric-vs-numeric and text-vs-text). Stable sort (original row order breaks ties).
  - This precompute-once design is also what makes the comparator a genuine total order: deriving "is this numeric?" independently for each pairwise comparison (the pre-fix design) could put two numerically-tied values (e.g. `"10"` and `"1e1"`) on opposite sides of a third, non-numeric value, since each comparison against that third value fell back to string collation independently and didn't have to agree with the other. A precomputed key removes that inconsistency by construction.
  - Performance: sorting 500k rows × 20 columns on 3 keys stays well under 1.2s (measured ~0.8s), including resolving each text column's collation rank once per distinct value rather than calling the collator again for every comparison.
- Persist sort per file.

### 4. Pagination
- A pager bar sits below the table, always visible (the table area scrolls between the toolbar/banners and the pager, not the pager itself). Controls, left to right: First « (icon button), Prev ‹ (title "Previous page (Alt+←)"), "Page [ N ] of M" (N is a number input — Enter or blur jumps, clamps to 1..M, invalid input restores the current page), Next › (title "Next page (Alt+→)"), Last », a row-range label, and a page size select (25/50/100/200/500, default 100).
- The row-range label is the user-visible row count (there's no separate visible status line any more — see "Toolbar, banners, and status", above): `"‹start›–‹end› of ‹Z› rows"`, or `"0 rows"` when Z = 0 (Z = filtered count). A `" (filtered from ‹total›)"` suffix is appended only when search/filters actually *reduced* the count below the file's total row count — not merely while a search or filter is active with no effect.
- Nav buttons disable via the `disabled` attribute when not applicable (First/Prev on page 1, Next/Last on the last page; all four when Z = 0).
- Page resets to 1 on quick search, filter rule, and sort changes. Column visibility changes and expand/collapse keep the current page. A live reload (`load` for the same fileKey) keeps the current page, clamped to the new page count.
- Changing page size keeps the first row currently shown visible: new page = `floor(firstRowIndex / newSize) + 1`. Changing page scrolls the table area back to top.
- The toolbar's single expand/collapse-all icon button toggles every row on the *current page only*; it shows a "collapse" icon/label once every row on the page is already expanded, an "expand" icon/label otherwise. Expanded state is keyed by row id, so it survives paging back and forth (and survives a page-size change that reshuffles which rows land on which page).
- Keyboard: Alt+→ / Alt+← move to the next/previous page when focus isn't in an input/select/textarea (so native text navigation and scrolling keys are untouched).
- `pageSize` is persisted per file as part of the view state; the current page number is not. A missing/invalid stored value (state saved before pagination existed) falls back to 100.
- Pure logic lives in `src/core/paging.ts` (`pageCount`, `clampPage`, `pageSlice`, `pageForRow`, `normalizePageSize`) — no DOM/vscode imports, unit-tested like the rest of `src/core`.

### 5. Banners, hints, and context menu
- **Malformed-quote warning**: shown above the table whenever quoting is on and the last parse's `quoteProblems` is non-empty (see Parsing, below) and the user hasn't dismissed it for this parse — "Quotes look malformed near row N. Rows after it may be merged into one.", a **Read Quotes as Plain Text** button (sets `quotes: false` and re-parses) and a dismiss (✕) button. Dismissal resets on every fresh parse, so a *new* quote problem is surfaced again even if an earlier one was dismissed.
- **Deleted-file banner**: shown while the host reports (via `fileDeleted`) that the open file was deleted on disk — `"‹name›" was deleted from disk. Showing the last loaded copy.` — and hidden again once the host reports (`fileRestored`) that it reappeared and reloaded. While the document has unsaved edits (see "8. Cell editing") the text is instead `"‹name›" was deleted from disk. Your unsaved edits are kept; saving will recreate the file.` — the host holds the file's bytes, so Ctrl/Cmd+S recreates it.
- **Changed-on-disk banner** (`#file-changed-banner`, `banner-warning`, `role="alert"`): shown while the host reports `fileChangedOnDisk` — which it sends instead of reloading when the file changes on disk *while the document is dirty* — `"‹name›" changed on disk. Your unsaved edits are kept; saving will ask before overwriting.` with a **Discard Edits and Reload** button (posts `revert`; the host runs VS Code's revert for this editor, which calls `revertCustomDocument` and reloads from disk — see Architecture) and no dismiss button (the condition persists until a revert or a save). Hidden by the next `load`.
- **Read-only banner** (`#readonly-banner`, `banner-info`): shown the first time per `load` that the user tries to edit (F2, double-click, **Edit Value**, a field's edit button) while the file is read-only for a *file-level* reason (`readOnlyReason` is `"encoding"`, `"filesystem"` or `"spans"` — see "8. Cell editing"), with that reason's sentence, a dismiss (✕) button, and an **Open as Text** button (same as the toolbar's). Never shown when editing is off by the `csvViewer.editing` setting (the user chose that; no affordances are drawn at all then).
- **Edit-error banner** (`#edit-error-banner`, `banner-warning`, `role="alert"`): shown when the worker rejects a commit (`editResult.ok === false`, see "8. Cell editing" for the two messages) (restored edits that no longer match are reported to the host with `editsDropped`, which warns once; the webview shows no banner for them); dismiss (✕) hides it, and the next successful commit or `load` hides it too.
- **Row-details hint**: a one-time banner — `"N more columns are in each row's details. Click a row's arrow to expand it, or change which with Columns."` — shown while at least one column is detail-only and the hint hasn't been seen yet. Dismissing it, or expanding any row for the first time, marks it seen: the webview tells the host (`hintSeen`), the host remembers the id in `globalState` (`csvViewer.hintsSeen`, not per-file), and every future `load` includes it in `hintsSeen` so it never reappears for that user, in any file.
- **Context menu**: right-click a table cell or a detail field's value opens a menu with **Edit Value** first (opens the same editor F2/double-click would — see "8. Cell editing"; when the file is read-only it is rendered dimmed (`aria-disabled="true"`, not `disabled`, so choosing it still shows the read-only banner) with the reason as its `title`, and it is absent entirely when the `csvViewer.editing` setting is off), then — only while that cell is edited-but-unsaved — **Revert Cell to "‹original, shortened to 40 characters›"** (commits an ordinary edit back to the baseline value, so it is itself undoable), then **Copy Value**; then (after a divider) **Show only rows where ‹column› = "‹value›"**, **Hide rows where ‹column› = "‹value›"** (the quick-add filters described under Filtering, above) and **Filter ‹column› by Values…** (closes the menu and opens the values picker for that column: under that column's header funnel when the column is in the table, otherwise at the click position, clamped inside the viewport); then (after another divider) **Copy Row as CSV** (one RFC 4180 line, every column in file order, quoted only where needed) and **Copy Row as JSON** (an object keyed by header, 2-space indented, every column). The row-level keyboard menu (Shift+F10 or the ContextMenu key on a focused row — there's no single cell/column in that context) offers only the last two, Copy Row as CSV/JSON. The menu is `position: fixed` and clamped inside the viewport, flipping left/up instead of overflowing right/bottom near an edge; Arrow Up/Down rove focus between its items, Escape closes it.

### 6. Keyboard and accessibility
- **Row focus (roving tabindex)**: exactly one data row is in the Tab order at a time (`tr.tabIndex`); the twisty/expand button is excluded from it (mouse-clickable, but Tab skips straight from row to row). ArrowDown/ArrowUp move the roving target to the next/previous row on the page; Home/End jump to the page's first/last row; ArrowRight/ArrowLeft expand/collapse the focused row (if not already in that state); Enter/Space toggle it; **F2** opens the inline editor on the focused row's first table-visible cell (Enter keeps its expand/collapse meaning — it does not start an edit — because the roving unit is the row, not a cell; see "8. Cell editing" for the editor's own keys: Enter / Ctrl+Enter commit, Escape cancels, Tab / Shift+Tab move the inline editor to the next / previous cell of the row); Shift+F10 or the ContextMenu key open the row-level context menu (see above). The target survives a re-render (sort/filter/page) by row id when possible, else falls back to the page's first row; it resets to the page's first row specifically when focus was on a row before the re-render (not merely restored to "the same id if present").
- Column header sort buttons stay in normal Tab order, each followed by its column's filter funnel (sort button, funnel, next column's sort button, …); repeatedly pressing Space/Enter on one keeps cycling its sort direction even though the header `<tr>` is fully rebuilt on every render — focus is restored to the same column's button by matching its label text, not DOM position (which could change due to a visibility change reordering/removing columns between renders) — and to the same *kind* of control: a focused funnel is restored to that column's funnel, a focused sort button to its sort button.
- **Cmd/Ctrl+F** focuses and selects the quick-search box (VS Code's webview shim swallows the browser's native Find, so this is the next thing most users try).
- **Alt+→ / Alt+←** change pages, except when focus is in an input/select/textarea (native cursor/selection behavior there is left alone).
- **Escape**: inside an open cell/field editor it cancels that editor (handled on the editor element with `stopPropagation`, so nothing below runs); otherwise closes the cell/row context menu if open, else the values picker if open (alone — a Filters panel underneath it stays open; focus returns to the funnel or values button it came from), else closes whichever popover is open (and returns focus to that popover's trigger button — unlike an outside click, which closes a popover too but leaves focus wherever the user clicked).
- **Undo / redo** (Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z, Ctrl+Y): with no cell/field editor open these keys are *not* handled by the webview at all — VS Code's webview host forwards them to the workbench, whose `undo`/`redo` commands drive the custom document's edit stack (see Architecture, "Undo and redo"). While an editor is open they are the editor's own native text undo/redo and must never reach the document stack — see the same section for the mechanism and its fallback.
- **Popovers** (Columns, Filters, Sort, File format, and the values picker — see "Filter by values", above, for how it layers over the Filters panel): anchored under their trigger button, clamped inside the viewport with an 8px margin (flipping above the trigger instead of overflowing the bottom edge), re-clamped on window resize. Opening one closes any other that's open and moves focus to its first relevant control (e.g. the Columns popover focuses its search box). An outside click or Escape closes the open popover; every one of its own controls joins the Tab order while it's open.
- **Accessibility semantics**: a sortable column header's `<th>` carries `aria-sort` ("ascending"/"descending"/"none"); a data row carries `aria-expanded`; the twisty button carries its own `aria-expanded`, `aria-controls` (pointing at the detail `<tr>`'s id), and an `aria-label` ("Show/Hide details for row N"); the Columns/Filters/Sort/File format toolbar buttons carry `aria-haspopup="dialog"`, `aria-expanded`, and `aria-controls`, and their popovers carry `role="dialog"` with an `aria-label`; each header funnel and each panel `.values-btn` carries `aria-haspopup="dialog"` and `aria-expanded` (true while its picker is open), the funnel's `aria-label`/`title` is `Filter ‹column› by values`, and the picker is `role="dialog"` labelled with its title; `#status-bar` is `role="status"`; the table carries `aria-busy="true"` while a request is in flight (see "Toolbar, banners, and status", above).

### 8. Cell editing
Existing cell values can be changed in place and saved back to the file; nothing else about the file's shape changes. This section is the user-facing contract; the document model, save/undo/backup mechanics and message protocol are under Architecture ("Document model and editing").

- **Scope.** Only the value of an existing data cell can be edited. Not in this version (see Non-goals): adding, deleting, moving or duplicating rows; adding, deleting, renaming or reordering columns. **Header cells are never editable** — renaming a column is out of scope, and the displayed name can differ from the file text anyway (dedupe `a_2`, empty → `column_N`). With "First row is header" off, the first record is an ordinary data row and is editable like any other.
- **When editing is available.** Editing is **on by default** and controlled by a new setting `csvViewer.editing` (boolean, default `true`, description: "Allow changing cell values in the table and row details. Nothing is written until you save."). Beyond the setting, a *file* is read-only in the viewer when any of these hold, in this precedence; the host decides and sends `editable` plus `readOnlyReason` in `load` (`"setting" | "encoding" | "filesystem" | "spans"`, absent when editable) — the webview can additionally flip to `"spans"` itself after the worker's `initResult` (below):
  - `"setting"`: `csvViewer.editing` is `false`. No edit affordances are rendered (no **Edit Value** menu item, no per-field edit buttons, F2 / double-click do nothing). Changing the setting takes effect in open viewers without a reload: the host listens to `onDidChangeConfiguration` and posts `setEditable { editable, readOnlyReason? }`; turning it off while a document is dirty keeps the existing edits (they can still be saved, undone, reverted) and only blocks new ones.
  - `"encoding"`: the file is not valid UTF-8. The host decodes with `new TextDecoder("utf-8", { fatal: true, ignoreBOM: true })` first and falls back to `{ fatal: false, ignoreBOM: true }` when that throws (`ignoreBOM: true` keeps U+FEFF in the text so character offsets line up with the bytes — `parseCsv`'s own `stripBom` still hides it from the table; this changes nothing visible). A lossy decode cannot be mapped back to bytes exactly (U+FFFD is three bytes, the invalid sequence it replaced often one), so such a file is read-only rather than risk silently re-encoding it. Sentence: `This file isn't valid UTF-8, so Wide CSV opens it read-only. Use Open as Text to edit it.` Latin-1 exports are the realistic case; detecting their encoding is a non-goal.
  - `"filesystem"`: `vscode.workspace.fs.isWritableFileSystem(uri.scheme) === false` (`undefined` = unknown counts as writable). Sentence: `This file system is read-only.`
  - `"spans"`: the worker could not map the parsed records back to the text exactly (`initResult.spansOk === false`, see "Record spans" under Parsing). Sentence: `Wide CSV couldn't match this file's rows to its text exactly, so it is opened read-only. Use Open as Text to edit it.` This is an internal safety valve; it is expected never to fire for a real file (the property tests drive the record splitter and Papa to agreement) but it is what guarantees a save can never corrupt a file when they disagree.
  - Untrusted workspaces: editing works. VS Code's Restricted Mode gates extension code, not file writes performed on the user's explicit save, and the extension already declares `untrustedWorkspaces.supported: true` because it runs no workspace code. `virtualWorkspaces: true` stays: writes go through `vscode.workspace.fs.writeFile`, the same provider-aware API as the reads; a provider that is not writable yields `"filesystem"` above.
  - A cell whose value is longer than `DETAIL_WARN_CHARS` (1 MB) is not editable in either editor (the per-field edit button is `disabled` with `title` `Too large to edit here (over 1 MB). Use Open as Text to change it.`; F2/double-click/**Edit Value** on it show the same sentence in the edit-error banner). The limit is about textarea performance, not truncation: an editor always holds the *full* raw value, never the 500-character table text or the 10,000-character detail text (both are render-only, `src/core/truncate.ts`).
- **Starting an edit — table.** Any data cell of a table-visible column (never the chevron cell, never a header) opens an inline editor on: **double-click** on the cell; **F2** while a data row has focus (opens on the row's first table-visible column — the roving-tabindex model has no cell focus, so F2 plus Tab / Shift+Tab is the keyboard route across a row; the details panel's per-field edit buttons are the keyboard route to a specific column); **Edit Value** in the cell context menu. If the cell's value contains a line break or is longer than `TABLE_CELL_MAX_CHARS` (500), the table does *not* edit it inline: the row is expanded (if it isn't) and the **details editor** for that field opens instead (the field is guaranteed to be in the panel by the "Also in table" rule in section 1), scrolled into view. Double-click and single-click coexist as follows: a `click` with `ev.detail >= 2` (the second click of a double-click) does not toggle the row; on `dblclick` of an editable cell, if the *first* click of that double-click toggled this row's expansion (tracked as `{ rowId, at }` of the last click-toggle, within 500 ms), that toggle is reversed before the editor opens — so a double-click ends with the row in the state it started in, at the cost of a brief flicker of the detail panel, which is accepted. Opening an editor clears any text selection the double-click made.
- **The inline editor.** The `td` gets class `editing` (`position: relative; padding: 0; overflow: visible`) and contains a single `<input type="text" class="cell-editor">` filling the cell (`position: absolute; inset: 0; width: 100%; box-sizing: border-box`), styled with `--vscode-input-background` / `--vscode-input-foreground` / a 1px `--vscode-focusBorder` border (`--vscode-contrastActiveBorder` outline in high-contrast), inheriting the cell's font and, for numeric columns, right alignment. Its `value` is the full raw value, selected on open, `aria-label` = `Edit ‹column›, row N` (N = `rowId + 1`, as in the twisty's label). Exactly one editor (inline or details) is open at a time; opening another commits the current one first. The row keeps the roving tabindex (`focusedRowId = rowId`).
  - **Enter** commits and closes; **Escape** cancels and closes (both `preventDefault` + `stopPropagation`, so the row's Enter-toggles-expansion and the global Escape handler do not run); **Tab / Shift+Tab** commit and open the editor on the next / previous table-visible cell of the same row (skipping cells that would redirect to the details editor is *not* done — they redirect, which expands the row; this is acceptable), and at the row's last / first cell commit and return focus to the row (Tab never traps); **blur** commits (clicking anywhere else, Alt+→ paging, the webview losing focus); Ctrl/Cmd+S commits synchronously in the keydown handler before VS Code's save runs (see Architecture for the flush handshake that makes this race-free); any re-render of the table body (page change, query result, column visibility change, `load`) commits an open editor first — a `load` *cancels* it instead, since its row ids are no longer meaningful. Ctrl/Cmd+Z / Y inside the input are the input's native undo/redo (see Architecture). A value typed into an `<input>` cannot contain a line break; pasted CR/LF are stripped by the browser.
  - **Commit** with a value equal to the cell's current value is a no-op (editor closes, nothing posted, nothing dirty). Otherwise `\r\n` and lone `\r` in the new text are normalized to `\n` (parsed values never contain `\r`; see Parsing), then: if quoting is off for this parse and the value contains the delimiter or a line break, the commit is rejected locally (edit-error banner: `With Quoted fields off, a value can't contain the separator or a line break.`; the editor stays open with the text); else the webview posts `editCell` to the worker, closes the editor, shows the new text in the cell immediately, and on `editResult.ok` records the edit and posts `edit` to the host (Architecture). On `editResult.ok === false` the cell text is restored and the edit-error banner shows `Couldn't edit row N: ‹reason›.` Focus after commit or cancel returns to the row (`focusRowById`), except for Tab, which moves to the next editor.
- **Starting an edit — row details.** Every detail field's `dt` gets, after the copy button, an **edit** icon button (`.field-edit-btn`, codicon `edit`, `aria-label` `Edit ‹field› value`, in the Tab order like the copy button). It, **Edit Value** in the field's context menu, and the table redirect above open the **details editor** in that field's `dd`: the `dd` gets class `editing` and its content is replaced by a `<textarea class="field-editor">` holding the full **raw** value (never the pretty-printed JSON, never rendered Markdown, never the Show-all-truncated text), `rows` = the value's line count clamped to 3..20, vertically resizable, same input colours as above, `aria-label` `Edit ‹column›, row N`; below it a `.field-editor-actions` row with **Apply** (class `primary`) and **Cancel** buttons and a muted hint `Ctrl+Enter to apply · Esc to cancel` (`⌘↩` on macOS, detected from `navigator.platform`). While a field is being edited, its copy button, format toggle, More/Less and Show all links are not shown (they return with the re-populated field).
  - **Enter** inserts a newline; **Ctrl/Cmd+Enter** or **Apply** commit; **Escape** or **Cancel** cancel; **blur** commits unless `relatedTarget` is inside the same `dd` (the Apply/Cancel buttons); the same re-render and `load` rules as the inline editor apply. The same no-op, normalization, quotes-off and rejection rules apply, with one addition: the textarea accepts line breaks, so a single-line table value can become multi-line (and vice versa) — the cell and the "Also in table" group follow the new value.
  - After commit or cancel the field is re-populated via `populateDetailContent` for that row (so the copy button copies the new value, the JSON Raw/Formatted toggle, Markdown rendering, the 6-line clamp and the 10,000-character cap all apply to the new value from their default states — Formatted for JSON, the column's Markdown mode, clamped, not Show-all), and focus moves to that field's edit button (the `dd` itself is not focusable and is rebuilt). Right-click inside the textarea is the browser's native menu (the `dd`'s `contextmenu` handler ignores events whose target is inside `.field-editor`); clicks and selections inside either editor never toggle the row (`onRowClick` returns when `ev.target.closest(".cell-editor, .field-editor")`). A rendered Markdown link in a field being edited is simply not there (the textarea replaced it).
- **After an edit.** The table cell (and, if the row is expanded, its detail field) shows the new value with the usual 500 / 10,000-character truncation; the cell's hover `title` is recomputed on the next `mouseenter` (`td.title` is cleared). **Edited-but-unsaved** cells are marked: `td.edited-cell` and `dd.edited-field` draw a 3px inset bar on the left (`box-shadow: inset 3px 0 0 var(--vscode-editorGutter-modifiedBackground, var(--vscode-focusBorder))` — the "modified" gutter colour, defined in every built-in theme including the high-contrast ones; under `@media (forced-colors: active)` the bar uses `Highlight` and the cell text gets `text-decoration: underline dotted`, since box shadows may be dropped there), carry `aria-description="Edited, not saved"`, and the `td` has `title` `Edited (not saved). Original: ‹original value, cut to 200 characters›` (prefixed to the clipped-cell title when both apply). Marks are keyed by row id and column index in the webview's `editedCells` map (`Map<rowId, Map<columnIndex, { original, current }>>`), so they survive paging, sorting, filtering and column-visibility re-renders, are cleared by `saved` (the values now match the file) and by any `load`, and are set/cleared by host-driven `applyEdits` (undo/redo). An edit is announced through a new visually-hidden `role="status"` region `#edit-status`: `‹column›, row N: changed to "‹new value, cut to 100 characters›"` on commit, `Undone: ‹column›, row N` / `Redone: …` on `applyEdits`, `All edits saved` on `saved`.
- **Filters, sort, search and counts are not re-evaluated by an edit.** The edited row stays exactly where it is, with its current page position, until the next worker `query` — a row vanishing the instant Enter is pressed would be disorienting and spreadsheets do not do it either. Row identity is always the **original record index** (`WorkerRow.id`), never the view index. The next query (any change of quick search, filter rules, sort keys, Clear Search / Turn Off Filters, or a `load`) sees the new values: the row may then stop matching, move, or start matching. To guarantee that, every applied edit (commit, undo, redo, restore) resets `lastQueryKey` to `null`, so the no-op query skip cannot serve a pre-edit view for an identical key (e.g. a rule toggled off and back on); the worker invalidates `sortKeyCache` and `distinctCache` for the edited column (so the values picker and the next sort reflect it). "Filtered: X of Y" and the pager range keep their pre-edit numbers until that next query. Column profiles (numeric right-alignment, auto-Markdown, the first-open table/detail split) are computed once per parse and are **not** recomputed on edit.
- **Padded cells.** A short row's missing trailing fields are shown as empty cells (the parser pads them). Editing one is allowed: the record is re-serialized with exactly as many fields as needed to include the edited one — `max(original field count, editedIndex + 1)` — never padded out to the full column count (minimal diff). Committing `""` into a padded cell is the no-op case above. Undoing such an edit shrinks the record back (trailing empty fields beyond the original count are dropped when comparing to the baseline, so an undone extension never leaves a stray trailing delimiter). A row with *extra* fields beyond the header (`column_N` auto-headers) has real fields there; they edit normally.
- **File format while dirty.** The Separator, custom separator, "First row is header" and "Quoted fields" controls, and the quote banner's **Read Quotes as Plain Text** button, are `disabled` while the document has unsaved edits **or an edit still in the worker** (the lock engages at the moment of commit, not when the worker answers), with `title` / a note in the popover `Save or revert your edits to change the file format.` The separator error's **Turn Off** link is disabled with them, and every handler (including the custom separator's 300 ms debounce and that link) refuses to re-tokenize while locked. The host enforces the same rule: a `saveState` whose delimiter, header or quote choice differs from the stored one is refused while the document is dirty (the stored format is kept and the webview gets a fresh `load`), and an `edit` whose `change.format` differs from the document's format is dropped with a `load`. Edits are addressed by record and field index under one tokenization; re-tokenizing underneath them is not defined and is not attempted. The first accepted edit of a file whose separator is **Auto** (no stored choice, no `.tsv`/`.tab` default) pins the detected separator into `ViewState.delimiter` (posting `saveState` before the `edit`), because an edit can change what auto-detection would pick and the saved file must reopen the way it was edited.
- **Open as Text.** Unchanged button; if the viewer is dirty, replacing its tab with the text editor is **refused** by the host with a warning `Save or revert your edits before opening as text.` (nothing is replaced). The alternative — letting `vscode.openWith(uri, "default")` replace the tab and trusting VS Code's "Do you want to save the changes?" dialog — could not be verified, and an unprompted swap would silently lose the edits. The text editor and the viewer are independent models of the file: when both hold unsaved changes, whichever saves second meets its editor's own conflict handling (VS Code's "content is newer — Overwrite / Compare / Revert" for the text editor; the viewer's overwrite prompt described under Architecture, "Save"). The viewer never reads from the text editor's buffer (see "Why a non-text custom editor").

## Parsing
- `src/core/csvParse.ts` (pure module, no vscode/DOM import) wraps [Papa Parse](https://www.papaparse.com/) as the tokenizer: quote-aware (`"` only opens a quoted field as the first character of a field — a stray mid-field `"`, e.g. an inch mark or `He said "hi"`, is literal text, not a quote-open), `""` escapes, newlines inside quotes, CRLF/LF/CR, BOM stripping, ragged rows (pad short rows with "", extra cells get auto headers `column_N`).
- **Line endings are normalized before Papa ever sees the text**: every `\r\n` and lone `\r` is converted to `\n` first. Papa sniffs a single newline style for the whole file from an early sample and then treats any *other* line-ending style as literal text rather than a row separator, so a file mixing CRLF/LF/CR (which real-world CSVs exported by different tools/OSes routinely do) used to silently merge rows and leak newline characters into cell values. Normalizing up front fixes that for the whole file — including inside quoted fields, so an embedded CRLF in a quoted field is now stored as LF. That's a deliberate, documented tradeoff (there's no way to tell "a CRLF that's part of quoted content" from "a CRLF that separates rows" without a full parse pass), not an oversight.
- `parseCsv(text, options)` public API: BOM strip, header dedupe (`name`, `name_2`, guaranteed collision-free against every other final header — see below), empty header → `column_N`, ragged-row padding, extra cells → `column_N` headers, `firstRowIsHeader` option, and a new `quotes` option (default `true`). It returns `{ headers, rows, delimiter, quoteProblems }`: `delimiter` is the delimiter actually used (from Papa's `ParseResult.delimiter`), so the UI can show it (e.g. "Auto (;)"); `quoteProblems` is covered below.
- Header dedupe never lets a generated `_N` suffix collide with any other final header, including one that is itself a later literal in the file: `"a,a,a_2"` — the literal `a_2` (3rd column) keeps its name; the duplicate `a` (2nd column) skips `a_2` (reserved for that literal) and becomes `a_3` instead. Every final header is guaranteed unique.
- **Malformed quoting**: a quote that opens right after a delimiter, closes, and is followed by more text before the next delimiter (e.g. `h,"b"c,d`) still makes Papa swallow the rest of the row (or, if it recurs, the rest of the file) into one field — that's inherent to quote-aware CSV parsing and isn't changed (the decision was to keep Papa rather than hand-roll different quote handling). What IS added: `ParseResult.quoteProblems: { row: number }[]` lists the first ~20 data-row numbers (1-based, as the user sees them) where Papa reported a quote-related error (`InvalidQuotes`/`MissingQuotes`/etc.). Papa reports every case where a bad quote swallows following rows; a `"` in the middle of an unquoted field raises no error because it parses correctly as literal text, so no banner is shown for it. The webview shows a dismissible warning banner above the table whenever `quoteProblems` is non-empty and quoting is on (see "Banners, hints, and context menu", above, for its exact copy and the "Read Quotes as Plain Text" button). That button (and the File format popover's "Quoted fields" checkbox, persisted per file as `ViewState.quotes`, default/fallback `true` for state saved before this field existed) sets `quotes: false` and re-parses: every `"` becomes literal text (Papa has no "off" switch for quoting, so this uses a `quoteChar` that can't occur in real text — a NUL sentinel, guarded against the rare case where the text already contains it). With quoting off, `"` also becomes a usable custom delimiter (see below) — the malformed-quote example above, re-parsed with `quotes: false`, correctly splits into 3 literal-quote-preserving fields.
- Blank lines (no characters at all) are skipped everywhere — via Papa's `skipEmptyLines: true` — both a trailing newline (no spurious empty row) and a fully blank line in the middle of the file. A line with only delimiters (e.g. `,,,`) is a real row of empty fields and is not skipped; this is a deliberate, documented choice, not an oversight.
- Delimiter: `ParseOptions.delimiter` — empty string or `undefined` means auto-detect via Papa's quote-aware guessing among `delimitersToGuess: [",", ";", "\t", "|"]`; a non-empty string (of any length, so multi-character delimiters like `||` are supported) forces that delimiter. `.tsv`/`.tab` files are given `"\t"` as the host's `defaultDelimiter`, used when no per-file separator is stored (see Custom separator, below). The old line-based `detectDelimiter` export and hand-written `tokenize` were removed along with the hand-written tokenizer; nothing needs a standalone delimiter guesser anymore since `parseCsv` returns the one it used.
- First row is header. Duplicate/empty header names get made unique (`name`, `name_2`; empty → `column_N`). The File format popover's "First row is header" checkbox (persisted per file); when off, headers are `column_1..N`. Toggling it re-parses locally in the webview from the text already held in memory — no host round-trip.
- `parseCsv` additionally exports `effectiveQuoting(text, quotes)` — `quotes || text.includes("\u0000")`, i.e. the quoting mode Papa was *actually* run with (the NUL sentinel can't be used when the text contains NUL, so quoting silently stays on) — and reports it as `ParseResult.quoting`. Everything that must agree with Papa about quotes (the record splitter and the serializer below) takes this effective value, never the raw option.

### Record spans (`src/core/recordSpans.ts`)
Editing needs to know, for every parsed row, exactly which characters of the original text it came from. Papa reports no offsets, and `parseCsv` normalizes line endings (shrinking CRLF), strips the BOM and skips blank lines before Papa sees the text, so offsets in what Papa parsed are not offsets in the file. A separate pure module recovers them from the **original** text and is checked against Papa at runtime.

- `splitRecords(text, { delimiter, quotes }): RecordSpan[]` with `RecordSpan = { start, end, eol, fieldCount }` — `start`/`end` are UTF-16 code-unit offsets into the original `text` (exclusive `end`, i.e. the record's bytes *without* its terminator), `eol` is the exact terminator that followed it: `"\r\n" | "\n" | "\r" | ""` (`""` only for a last record at EOF), `fieldCount` is the record's physical field count before any padding. `delimiter` is the delimiter Papa actually used (`ParseResult.delimiter`) and `quotes` the *effective* quoting (`ParseResult.quoting`). The text between consecutive spans (a BOM at offset 0, blank lines, the terminators themselves) is never part of any span and is preserved verbatim on save.
- The splitter is a single forward pass that reproduces Papa's record boundaries, and *only* its boundaries — it never produces field values. Rules, mirroring `Papa.Parser.parse`'s quoted-field branch (the implementer should read that function; the property tests below are the proof): a leading U+FEFF is skipped; `\r\n`, `\n` and `\r` each terminate a record outside quotes (equivalent to `normalizeLineEndings` + split on `\n`; `\n\r` is a terminator followed by an empty line); a field is quoted only when `"` is its first character (right after record start or a delimiter); inside quotes, `""` is an escaped quote (checked *before* anything else, as Papa does); a lone `"` followed by any number of U+0020 spaces and then the delimiter, a terminator or EOF closes the field (Papa's "spaces between closing quote and delimiter" rule) — otherwise that `"` is literal and the field stays open (Papa's malformed-quote recovery, which is what makes `h,"b"c,d` swallow the rest of the line or file: it keeps searching for the next quote that *is* followed by a delimiter/terminator); a quoted field that never closes runs to EOF; with `quotes: false` the quote character is literal everywhere. Multi-character delimiters match as a string; `"` as the delimiter is only reachable with quoting off. A record is **skipped** (not emitted) when it would parse as a single empty field — empty text, or (quoting on) exactly `""`, optionally followed by spaces — which is Papa's `skipEmptyLines: true` test (`data.length === 1 && data[0] === ""`); a whitespace-only line, `,,,` and `""""` are real records.
- **Agreement with Papa is enforced, not assumed.** The worker runs `splitRecords` right after `parseCsv` on every `init` and sets `initResult.spansOk = spans.length === (headers were taken from the file ? rows.length + 1 : rows.length)`; a mismatch makes the file read-only (`readOnlyReason: "spans"`) and is logged with `console.error` — nothing else changes. For texts over 8 MB the pass would hold up the first render, so it runs in 8 ms slices after the first queries are answered: `initResult` then omits `spansOk` and a `spansReady { requestId, spansOk }` message follows (the webview flips to `"spans"` on a `false`); an edit, restore or rebase that arrives earlier finishes the scan itself. On every commit the worker re-parses just that record's text **including its terminator** (`parseCsv("\n" + text.slice(start, end + eol.length), { delimiter, firstRowIsHeader: false, quotes })` — the terminator because Papa only closes `"a" ` before a terminator, the leading newline so that a U+FEFF at the start of the record is not taken for the file's BOM) and requires exactly one row whose fields equal the record's baseline (unpadded) fields; otherwise the edit is rejected (`reason: "the row's text couldn't be matched exactly"`). The same re-parse is applied to the record **as the host will write it** — the edited cell, the record's own fields, and every other cell of that record already edited (pending edits to padded columns further right are written too; checking only up to the edited column let `a|` before a pending third column write `a|||||x`, which a `||` file reads back as `a`, ``, `|x`) — and the edit is rejected if it does not come back as the intended fields (e.g. an empty value in a one-column file, which would make the row vanish (in a wider file the row is written as `,`, see Architecture); a value starting with U+FEFF in the file's first record; with Quoted fields off, any NUL, and any change to a cell that holds the NUL that is forcing quoting on — a NUL is what makes Papa read quotes again, so adding or removing one would re-tokenize the whole file). So a disagreement between the splitter and Papa — the one way a save could write a record into the wrong place — is caught before it enters the edit list.
- The worker keeps the span table in typed arrays (`Uint32Array` for `start`/`end`/`fieldCount`, `Uint8Array` for the `eol` kind — two million records as objects would cost ~160 MB) and, in one additional pass over the text at `init`, a parallel table of **UTF-8 byte offsets** (`byteStart`/`byteEnd`, computed with `utf8Length` below; U+FEFF counts its 3 bytes, surrogate pairs 4), built lazily at the first edit or rebase and aliased to the character offsets when the text is pure ASCII. They are reported in `CellChange.record` for tests and tooling; **the host does not trust them** — it finds record boundaries by splitting the bytes it holds (Architecture, "Save"). They are only exact for valid UTF-8, which the host's `"encoding"` read-only rule guarantees for any file that can be edited. The worker also retains the original `text` for the document's lifetime (it is needed for span slicing and the per-commit re-parse); the main thread already retained its copy, so the webview now holds the text twice persistently instead of once plus a transient copy.

### Serialization and splicing (`src/core/csvSerialize.ts`, `src/core/csvEdit.ts`)
- `needsQuotes(field, delimiter)`: true when the field contains the delimiter string, `"`, `\n` or `\r`, or starts or ends with a space or tab (leading/trailing blanks are quoted so tools that trim unquoted fields — and Papa's own spaces-after-quote rule — can't change the value), or, with a multi-character delimiter, ends with a proper prefix of it (`a|` before `||` would read back as `a` plus `|||` split at the first `||`); an empty field is never quoted. `serializeField(field, delimiter, quotes)` returns the field as-is or wrapped in `"…"` with embedded `"` doubled; with `quotes === false` it returns `null` only when the field contains the delimiter or a line break (nothing can be escaped; the caller — the webview's commit path — rejects the edit); `"` and leading/trailing blanks are then written literally, since they are literal text in that mode. `serializeRecord(fields, delimiter, quotes)` joins the fields with the delimiter and **no terminator**; precondition: no field contains `\r` (parsed values never do; the editors normalize typed text). `utf8Length(s, from?, to?)` is the UTF-8 byte length of a string slice, exact for well-formed UTF-16 (a lone surrogate counts 3, like `TextEncoder`).
- Re-serialization is **per record**: a record with at least one field that differs from its baseline (see "edited-ness" under Architecture) is replaced in full by `serializeRecord(currentFields, delimiter, quoting)` — its unedited fields are written by the same rule, so redundant quotes on them can disappear (`"a",b` with `b` → `c` becomes `a,c`) and an embedded CRLF that the parser normalized to LF is written as LF; its original terminator (`eol`) is kept, as are the record's own preceding and following gaps. Everything outside edited records is copied byte for byte: BOM, quoting, line endings (mixed CRLF/LF/CR included), blank lines, whitespace-only lines, short rows' missing fields, the presence or absence of a final newline. Only `quoting` and `delimiter` of the current parse are ever used to write; the saved file therefore re-parses with the same options to the same table with the edited cells changed — that round trip is the central property test.
- `csvEdit.ts` is the pure splice used by both the unit tests and the host: `spliceText(text, spans, records: { index, fields }[], delimiter, quotes): string` and `spliceBytes(bytes: Uint8Array, records: { byteStart, byteEnd, fields }[], delimiter, quotes): Uint8Array` (ascending, non-overlapping, bounds-checked — it throws rather than write a partial result on any violation), plus `rebaseSpans(spans, byteSpans, records, delimiter, quotes)` which returns `{ spans, byteSpans }` for the spliced output without re-splitting (`rebaseSpanTable` is the same over the worker's typed `SpanTable`; `textPatches` / `applyTextPatches` express a splice as ascending `{ start, end, text }` replacements, which is how the worker tells the main thread about a save without sending the whole text) (each edited record's new char/byte length shifts every later offset; its `fieldCount` becomes its serialized field count). `encode(spliceText(…)) === spliceBytes(encode(…))` and `rebaseSpans(…) deepEquals splitRecords(spliceText(…))` are property tests.

### Custom separator
- The **File format** toolbar button (gear icon) opens a popover with a "Separator" dropdown, the custom-separator input, "First row is header", and "Quoted fields" (see above); the button's own tooltip/`aria-label` states the current format in full (e.g. "File format: comma, first row is header, quoted fields on"), since the button carries no visible text.
- "Separator" dropdown: `Auto (<detected>)` (e.g. `Auto (;)`, with a tab rendered as the word "Tab"), `Comma (,)`, `Semicolon (;)`, `Tab`, `Pipe (|)`, and `Custom…`. Custom reveals a small text input (max 5 chars, applied on input after a 300ms debounce); the typed value is **not trimmed** (a single space or a tab is a valid 1-character delimiter someone might actually type here), only a truly empty input falls back to Auto. `"` is rejected with an inline error (`Can't use " while Quoted fields is on.`, with a **Turn Off** link that unchecks "Quoted fields" and applies the pending custom value in one click) and never applied while quoting is on — Papa's `quoteChar` conflicts with it, and Papa also hardcodes `"` as an always-bad delimiter (`Papa.BAD_DELIMITERS`) regardless of `quoteChar`, so `parseCsv` works around that internally (substituting a delimiter Papa will accept before parsing) whenever `"` is requested with `quotes: false`. With quoting off, `"` **is** allowed as the custom delimiter.
- Persisted per file in `ViewState.delimiter` (`""` = auto). Values stored before this field existed lack it entirely — treated the same as `""`.
- Precedence when resolving what to actually parse with: the stored per-file choice, else the host's `defaultDelimiter` (tab for `.tsv`/`.tab`), else real auto-detection.
- Changing the separator re-parses locally from the held text, reconciles column visibility (new header names follow the content-based default rule — see "Column visibility", above; a name that existed before, even coincidentally, keeps its prior visibility), resets to page 1, and posts `saveState`. Filter rules are left as-is, but no longer misbehave when stale: a rule pointing at a column that no longer exists is *ignored* (see Filtering, above), not applied as "matches nothing" — the fix that stops a single stale include rule from hiding the entire file applies here too, the same as after a header rename. Sort keys pointing at a missing column are unaffected either way (already silently skipped).

## Architecture
- `CustomEditorProvider<CsvDocument>` (0.8.0; 0.4–0.7 used `CustomReadonlyEditorProvider`, v0.3 `CustomTextEditorProvider` — see "Why a non-text custom editor" below), registered with `supportsMultipleEditorsPerDocument: false` and `retainContextWhenHidden: true`, viewType `csvViewer.table`, priority `option` (text editor stays default). Selector `filenamePattern`s are `*.[cC][sS][vV]`, `*.[tT][sS][vV]`, `*.[tT][aA][bB]` — character classes so `DATA.CSV`, `Data.Tsv`, etc. match too (VS Code's plain `*.csv`-style pattern matching is case-sensitive; a bare lowercase pattern silently didn't match uppercase-extension files in "Open With…"). Menu `when` clauses use `resourceExtname =~ /^\.(csv|tsv|tab)$/i` (a case-insensitive regex) for the same reason — `resourceExtname` preserves on-disk casing and `==` is case-sensitive, so the old `resourceExtname == .csv || ...` clauses never showed "Open in CSV Viewer" for an uppercase-extension file's Explorer/editor-title/palette entries. Commands: `csvViewer.open` ("Open in CSV Viewer") available in explorer context menu, editor title bar (icon) for csv/tsv files, and command palette; `csvViewer.openAsText` from inside the viewer.
- `openCustomDocument(uri, openContext)` creates the `CsvDocument` and **reads the file** (`stat` for the size limits, then `vscode.workspace.fs.readFile(uri)`), keeping the result as `document.bytes` (a `Uint8Array`; see "Document model and editing" for why the host holds bytes for the document's lifetime). It never throws for a read error or an over-limit file: the document opens with `bytes = undefined` and a `loadError`, and `resolveCustomEditor`'s first `load` attempt reports it with the same notifications as before (`CSV Viewer: could not read …`, `… is larger than 512 MB and was not loaded.`), keeping the existing integration expectations. With `openContext.backupId` set, it also restores the edit list from that backup (below). `resolveCustomEditor(document, webviewPanel)` wires the panel: on the webview's `ready` it decodes `document.bytes` (`TextDecoder`, `ignoreBOM: true`, `fatal` first — see section 8's `"encoding"` rule; BOM handling for the *table* stays in `parseCsv`, unchanged) and posts `load`. Reading and writing through `workspace.fs` — instead of a synced `TextDocument`, which is what `CustomTextEditorProvider` required — is also why `capabilities.untrustedWorkspaces.supported` and `capabilities.virtualWorkspaces` are both declared `true` in package.json: there's no arbitrary code execution, writes happen only on the user's explicit save, and both reads and writes go through the same virtual-filesystem-aware API a virtual workspace provides for any other extension.
- **Why a non-text custom editor** (the "Why readonly" rationale of 0.4–0.7, which still holds): VS Code will not sync a text document to a `CustomTextEditorProvider` above a size ceiling of its own (~50 MB in 1.139.1) — `resolveCustomTextEditor` simply never ran for a file that big, no matter what this extension warned about. Reading bytes directly with `workspace.fs.readFile` bypasses that ceiling entirely (verified: 51 MB and 120 MB files open and render, in ~2s and ~5s respectively in this environment — see the integration suite's `largeFiles.itest.ts` for current numbers). 0.8.0 moves from the readonly provider to the full `CustomEditorProvider` — the *non-text* custom editor API, which keeps the byte-level read path and adds VS Code's standard dirty / save / undo / backup model on top — rather than back to a text editor provider. The trade-off is unchanged and deliberate: **unsaved edits in a side-by-side text editor are not reflected in the viewer, and the viewer's own unsaved edits are not reflected in a text editor.** The two are independent models of the same file until one of them saves (see section 8, "Open as Text"); the viewer only ever reflects what is on disk plus its own unsaved edits.
- **Size limits**: above 50 MB (checked via `vscode.workspace.fs.stat(uri).size` — an exact byte count, not the `document.getText().length` estimate v0.3 used, since there's no `TextDocument` to estimate from any more) shows a "may be slow" warning and still loads, same threshold as before. A new, harder line: above **512 MB**, an error is shown and the file is not read or loaded at all, so an enormous file can't be dragged into memory and wedge the extension host. (Measured: 513 MB is rejected via `stat()` alone, no `readFile`, in a few seconds.)
- **Live reload**: a `vscode.FileSystemWatcher` on exactly the open file — `new vscode.RelativePattern(vscode.Uri.joinPath(uri, ".."), basename)` — not a workspace-wide watcher, so it works for a file outside any open workspace folder too (this is also why virtual/untrusted workspace support is safe: the read path is identical everywhere). On change, debounced 300ms per document (so a burst of rapid saves — or a rewrite that lands in several small writes — coalesces into one reload) and cancelled on dispose, the file is re-read and a fresh `load` is posted, same as v0.3's re-send — **when the document is clean**. The watcher, its subscriptions and the debounce timer now live on the `CsvDocument` (one document ↔ one panel, since `supportsMultipleEditorsPerDocument` is `false`) and are disposed in `CsvDocument.dispose()`, which VS Code calls when the last editor for it closes; the panel's `onDidDispose` still disposes the panel-level subscriptions (messages, view state). **While the document is dirty** the watcher never reloads: a change (or a create after a delete) whose `stat` differs from `lastLoaded` posts `fileChangedOnDisk { name }` instead (its banner is in section 5; the stale `lastLoaded` is also what makes the save-time conflict check below fire), and the user chooses between **Discard Edits and Reload** (→ `revert` → VS Code's revert → `revertCustomDocument`, which reloads) and saving (→ overwrite prompt). The host's own write in `saveCustomDocument` updates `lastLoaded` from a `stat` taken right after `writeFile`, before returning, so the watcher event it triggers is recognized as "unchanged" and skipped. On delete (after a short grace period, since an atomic save looks like a delete immediately followed by a create/change), a **non-modal warning** (`CSV Viewer: "‹name›" was deleted. Showing the last loaded contents.`, or `… Your unsaved edits are kept; saving will recreate it.` when dirty) is shown and the webview is told via `fileDeleted` (see its banner, above) — nothing is re-read; the webview already holds the last successfully parsed data in memory and keeps showing it, the host still holds `document.bytes`, and a dirty document can be saved, which recreates the file (`writeFile` creates; the conflict check treats "no file" as "no conflict").
- **Rename**: a global `vscode.workspace.onDidRenameFiles` listener (registered once in `activate()`, not per panel) moves the renamed file's `workspaceState` entry from the old uri's key to the new one, and deletes the old key — both for a plain file rename and, by also matching any key nested under the old prefix, for a folder rename that carries files underneath it. A viewer left open on the renamed-away file keeps working: since its `FileSystemWatcher` still targets the *old* path, VS Code reports that as a delete (see above) — the viewer shows the "file was deleted" warning and keeps its last-loaded contents rather than trying (and failing) to follow the rename to the new path. Opening the file at its *new* path picks up the migrated state, so it doesn't go through fresh first-open reconciliation the way a genuinely new file would.
- **Parsing happens in the webview, not the host** (for performance — see below). The host never calls `parseCsv`; it only reads the file's bytes and ships the decoded text once per load/reload (and, for editing, splices bytes it is handed exact spans for — it still bundles no `papaparse`). Webview → host messages (`WebviewToHostMessage`, `src/core/types.ts`): `ready`, `saveState(state)`, `openAsText`, `hintSeen(id)` (see "Banners, hints, and context menu", above), the editing messages `edit`, `revert`, `flushed`, `synced` and `resync` (defined under "Document model and editing", below; `editorState` exists only if the undo-key fallback described there is needed), and — only when the host activated with its test-hook env var set — `rendered(rowCount, headers)` and `testCellValue`. Host → webview (`HostToWebviewMessage`): `load({ fileKey, text, state, defaultTableColumns, defaultDelimiter, hintsSeen, testHooks?, baseVersion, editable, readOnlyReason?, pendingEdits })` — `text` is the whole file's decoded text (not `headers`/`rows`), `defaultDelimiter` is `"\t"` for `.tsv`/`.tab` else `""`, `hintsSeen` is the per-user set of already-dismissed hint ids from `globalState`, and the last four are the editing fields (below); `fileDeleted({ name })` and `fileRestored` (see the deleted-file banner, above); and the editing messages `fileChangedOnDisk`, `setEditable`, `applyEdits`, `saved`, `flushEdits`, `editsDropped` (and `inlineUndo`/`inlineRedo` only under the undo-key fallback), plus the test-hook-only `testEditCell`, `testOpenEditor` and `testGetCell`.
- **Parsing, filtering, and sorting run in a dedicated Web Worker (`src/webview/worker.ts`, bundled to `out/webview/worker.js`), never on the main/UI thread.** A catastrophic regex (e.g. `(a+)+$`) or a large filter/sort used to block the whole webview outright (measured at 200k rows: 2.6s to first render, 1.3s to add a filter). The worker owns the full parsed dataset; the main thread only ever holds small summaries (headers, `detectedDelimiter`, `quoteProblems`, total/filtered row counts) plus the *current page's* rows, with full, untruncated cell values (truncation is render-only — see "Huge cells", below). It never posts the full rows array back.
  - Protocol (`src/webview/workerProtocol.ts`): `init` (once per load/re-parse: the whole text + parse options) → `initResult` (headers/detectedDelimiter/quoteProblems/totalRows, plus `quoting` — the effective quote mode — and `spansOk`, see "Record spans"); the editing requests `editCell`, `setCells` and `rebase` (defined under "Document model and editing", below); `query` (`quickSearch`/`filterRules`/`sortKeys`, whenever any changes) → `queryStarted` (posted right before `applyFilters` begins) → `filterDone` (posted right after `applyFilters`, before sorting) → `queryResult` (filtered count only — the worker caches the filtered+sorted row order, as row ids); `page` (page/pageSize) → `pageResult` (that page's rows); `distinct` (`column`) → `distinctResult` (`column`, `values: { value, count }[]`, `truncated` — the values picker's list, counted over the whole file rather than the filtered view, an unknown column answering with an empty list; cached in a `Map` per column name until the next `init`). If the worker is terminated and recreated by regex-timeout recovery while a `distinct` request is pending, the main thread re-sends it once the fresh worker's `initResult` arrives, so the picker never hangs on "Loading values…"; a fresh parse (`load`, separator/header/quote change) instead closes the picker. Paging alone (Next/Prev/page-size change) only ever sends `page` — it never re-filters/re-sorts. Every request carries a monotonically increasing request id, echoed back unchanged, so the main thread can recognize and drop a stale response (e.g. an in-flight quick-search query superseded by a newer one before it answers) rather than ever rendering it.
  - **No-op query skip**: `runQuery()` (`src/webview/main.ts`) computes a canonical key from quickSearch, sort keys, and only the *active* filter rules (`enabled && isRuleActive(...) && !timedOut`, reduced to their semantic fields — including `values` for `in` rules, so ticking a different set is a real change) — see `buildQueryKey`. If that key is unchanged from the last query actually sent, no `query` message goes out at all; only the desired page is (re-)fetched from the worker's already-correct cached view. This is what makes an intermediate filter-rule edit — adding a still-empty rule, picking its column or operator before it has a value — free: none of those change which rules are *active*, so the key doesn't change either. `requery()` is shared by quick search, every filter-rule control, and sort, always resetting to page 1 — filter-rule controls (column/operator/value/case/enabled/mode, add/remove) additionally share one 150ms debounce (`FILTER_RULE_DEBOUNCE_MS`) so a multi-field edit (column, then operator, then value) coalesces into the single query that reflects its *final* state, on top of the no-op skip itself.
  - **Sort-key cache** (`worker.ts`): a column's resolved sort key (empty/numeric/text kind, plus a collator-ranked text index — `src/core/sort.ts`'s `ResolvedCellSortKey`, via the newly-exported `buildColumnSortKeys`) is computed once, over the *entire* dataset, the first time that column is used as a sort key, and reused for every later query until the next `init` invalidates it. Re-sorting a filtered subset after that (`sortRowIdsByCachedKeys`, also exported from `src/core/sort.ts`) is then just stable integer/rank comparisons over however many rows survived filtering — never re-deriving each cell's kind or re-running the collator over the column's distinct values again. Sorting a subset by ranks computed over the *full* dataset produces identical relative order to computing them over just that subset (a value's collator-equality with another is independent of what else is in the ranked set) — this equivalence, and that the cached-key path orders exactly like plain `sortRows`, is covered by unit tests including a fast-check property in `src/test/sort.test.ts`. `sortRows` itself is now implemented in terms of these two functions (so it can't silently drift from them) and its own behavior/tests are unchanged. `buildColumnSortKeys` itself picks between two ranking paths depending on the column: with 20,000 or fewer distinct text values (`DISTINCT_TEXT_HASH_LIMIT` in `src/core/sort.ts`), it ranks each distinct value once via a `Map` and looks the rank up per cell; above that (a mostly-unique text column — names, ids, free-text notes), hashing every distinct value into a `Map` costs more than sorting row indexes directly, so it instead sorts the text cells' own indexes by the collator and hands out ranks in one pass, with no per-string hashing. Both paths give collator-equal values (e.g. `"a"`/`"A"`) the same rank either way.
  - **Regex timeout**: a `query` containing an enabled, syntactically-valid regex rule is tracked as "at risk"; the actual 2000ms watchdog for that specific request only starts once the *worker* confirms it has begun running (`queryStarted`), and is disarmed the moment filtering finishes (`filterDone`), before any sorting happens. This — not arming at send time — is what a request merely queued behind an earlier one (or paired with a slow sort afterward) needs: it's never penalized for time spent waiting its turn in the worker's single-threaded mailbox, or for a slow sort that isn't the regex's own doing. If the watchdog does fire (presumed stuck in catastrophic backtracking), the stuck worker is `terminate()`d, a fresh one is created, the offending rule(s) are added to a webview-only `timedOutRuleIds` set and excluded from every future query the same way an invalid regex is excluded (`isRuleActive`/`applyFilters` themselves are untouched — the exclusion happens by never sending that rule to the worker), the fresh worker is re-initialized with the same text/options, and the query re-runs without the disabled rule(s). The Filters panel shows "Skipped: pattern took over 2 s. Edit it to retry." (see Filtering, above); editing that rule's value clears the mark immediately (before the next query even answers) and gives it a fresh chance. A page navigation requested while a query is in flight (including during regex-timeout recovery) is queued (`pendingPageAfterQuery`) and applied once the in-flight query settles, rather than dropped — the main thread is never blocked by the worker regardless, so the UI (including pager buttons) stays responsive throughout.
  - **Working indicator**: a 2px indeterminate progress bar (`#working-indicator`, see "Toolbar, banners, and status", above — it replaced an earlier plain-text "Working…" label), shown only once an interactive request (filter/sort/search/page change) has been in flight longer than 150ms, with `aria-busy="true"` set on the table meanwhile, and hidden the moment the corresponding render completes. Never shown during the initial `load` (which already shows "Loading…").
  - **CSP / loading under a webview**: a webview can't load a `vscode-resource:` URI directly as a `Worker` script. `buildHtml` (`extension.ts`) passes the worker script's webview URI via a `data-worker-src` attribute on `#app`; the webview fetches that URI's *text* (allowed by the CSP's `connect-src ${webview.cspSource}`) and loads it from a `Blob` URL instead (allowed by `worker-src blob:`). The Playwright harness (`src/test/webview-e2e/harness.ts`) exercises the identical code path via a routed fake URL rather than skipping it, and the integration suite (`npm run test:integration`, real VS Code) is what actually proves the Blob-URL approach works under the real webview CSP — the Playwright harness alone doesn't prove that.
- The webview's `onLoad` handler shows "Loading…" in the status bar and yields one frame (`requestAnimationFrame`/`setTimeout 0`) before creating/using the worker, so the placeholder actually paints before a large parse starts. It reconciles column visibility itself once the worker's `initResult` answers (the host no longer does — `defaultVisibility`/`reconcileVisibility` are webview-only) and only posts `saveState` back if reconciliation actually changed the stored visibility map, so a plain reopen of an already-settled file doesn't write on every open. The webview holds onto `text` in its in-memory state so the "first row is header" toggle and separator changes (see Custom separator, above) can re-send it to the worker (a fresh `init`) without another host round-trip.
- **Document model and editing** (0.8.0). Ownership is split so that saving never depends on the webview, and the webview never has to trust its own offsets:
  - **The host owns the authoritative file content and the edit list.** `CsvDocument { uri, bytes: Uint8Array | undefined, lastLoaded: { size, mtime } | undefined, baseVersion: number, saveBase: number, epoch: number, format: { delimiter, quoting } | undefined, records: Map<recordIndex, RecordState>, edited: Set<recordIndex>, queue: Promise, loadError?, lossy: boolean, watcher…, dispose() }` with `RecordState = { originalText: string, originalFields: string[], fields: string[], floor: number }`. **Records carry no offsets**: `bytes` is the file exactly as last loaded or saved, and at save time the host splits those bytes itself (`splitRecordsToTable` + `addByteOffsets` with `document.format`, i.e. the same Papa-faithful scan the worker ran) and locates each record by index, so a webview offset can never move a write. `bytes` is kept for the document's lifetime: save, Save As, backup, revert and "save after the file was deleted" must all work while the webview is hidden (VS Code only reliably delivers messages to a visible webview — `multiPanel.itest.ts` documents this) or gone, and a splice must never run against bytes that differ from what the user saw. Cost: one copy of the file in the extension host, up to 512 MB, off the V8 heap. `baseVersion` increments on every change of `bytes` (first load, reload, save) and every `load`, `saved`, `applyEdits` and `edit` message carries it; the webview ignores host messages for a base it hasn't reached and the host ignores an `edit` for a stale base (and answers it with a fresh `load`). `saveBase` is the `baseVersion` of the last save; `epoch` bumps whenever `records` is discarded (reload, revert, a dropped edit), so an undo/redo closure created in an earlier epoch is a no-op. `floor` is the record's field count when it was first touched: trailing empty fields above `floor` are not written (`fieldsForWrite(fields, floor)`), which is what lets undoing an edit of a padded cell restore the original bytes (`a,b,c\n1\n` stays `1`, not `1,,`), including after a save in between. **The host is the one owner of floors**; the worker needs them to validate what the host will write, so they travel: `load.recordFloors: { recordIndex, floor }[]` lists every held record whose floor is below its field count (the only case the webview cannot derive from the file), `saved.written[].floor` carries the floor of each record just written, the main thread keeps them in `AppState.recordFloors` and hands them to the worker in every `init` (a re-parse or a regex-timeout respawn included), and `rebase` applies `written[].floor`. A format change clears them with the host's records. Without this a reload after a save left the worker believing the saved field count was the floor, so blanking the cells of a once-padded row passed the worker's check while the host trimmed the record to one empty field, i.e. an empty line, i.e. a deleted row. **A row that edits have emptied is not a blank line.** One empty field serializes to an empty line, and blank lines are not records, so the row would be gone on reopening. What the host writes for a record is `recordFieldsForWrite(originalFields, fields, floor, columns)`: `fieldsForWrite`, except that in a file with more than one column (`RecordInfo.columns`, kept in `RecordState.columns` and in the backup) a result of a single empty field is written as **two** empty fields (`,`), which reads back as the same all-empty row, unless the record was a single empty field to begin with (then it is unchanged). Edited-ness, the worker's validation, the backup and the save all use this one function, so undoing back to the original still writes the original bytes. In a genuinely one-column file there is no such form, so the worker refuses the edit (`an empty value would leave this row empty, which removes it from the file`). As the last line of defence the host refuses an `edit` that would still produce a single empty field (a forged or buggy message) with a `load` followed by `editRefused { message }`, which the webview shows in the edit-error banner, and `buildOutput` throws the consistency error for such a record. `records` holds state for every record the webview has reported (an edit, or a backup restore); `edited` is the subset whose written fields currently differ from `originalFields` (`isRecordEdited(original, fields, floor)`: "edited-ness"). The host's dirty notion is `edited.size > 0`; VS Code's own notion (undo-stack position vs save point) agrees except for stale stack entries, below. **`lossy`** (the file does not round-trip through UTF-8, so the `"encoding"` read-only rule applies) makes the host reject every `edit`. `exclusive(document, fn)` is a per-document promise queue: save, Save As and revert run one at a time, in arrival order.
  - **The worker owns the parsed model and the spans** (`rawRows`, the typed-array span tables, `text`, an `originals: Map<rowId, Map<columnIndex, string>>` of baseline values for touched cells — an entry is dropped again when the cell returns to its baseline). Requests: `editCell { requestId, rowId, columnIndex, value }` → verifies (section 8 / "Record spans": the record's span text re-parses to its unpadded fields), applies `rawRows[rowId][columnIndex] = value` in place (array identity is the row-id key, so it must not be replaced), extends the padded array if needed, invalidates `sortKeyCache`/`distinctCache` for that column, records the baseline on first touch, and answers `editResult { requestId, ok: true, change }` or `{ requestId, ok: false, reason }`; `change: CellChange = { rowId, recordIndex, columnIndex, oldValue, newValue, record: { charStart, charEnd, byteStart, byteEnd, eol, fieldCount, originalText, originalFields }, format: { delimiter, quoting } }` (`originalText` = `text.slice(charStart, charEnd)`, `originalFields` = the record's unpadded baseline fields; both are included on every edit — the host de-duplicates — so one message carries everything the host needs to serialize and verify that record). `setCells { requestId, cells: { rowId, columnIndex, value }[] }` applies values without verification (the host is authoritative for undo/redo/restore) and answers `setCellsDone { requestId }`; `rebase { requestId, written? }` applies what the host just wrote: for the listed `written: WrittenRecord[] = { recordIndex, fields }[]` (or, when absent, for every record whose current fields differ from their baseline) it recomputes the span tables via `rebaseSpanTable`, sets those records' baselines to the written fields (and their `floors` to the written field count), keeps everything else — in particular a cell edited while the save was writing stays an edit against the new baseline — and answers `rebased { requestId, patches: TextPatch[] }`; the main thread applies the patches to its own copy of `text` with `applyTextPatches` instead of receiving the whole text. `initResult.spansOk` is optional (absent for texts over 8 MB, followed by `spansReady`; see "Record spans"). `recordIndex = rowId + (firstRowIsHeader ? 1 : 0)`.
  - **The main thread** keeps `editedCells` (section 8) for rendering and announcements, the single open editor, and `baseVersion`. Commit path: `editCell` → on `ok`, update `editedCells` (an entry whose `current` equals its `original` is removed, so **Revert Cell** or retyping the original clears the mark), reset `lastQueryKey`, pin the detected separator if the viewer is on Auto (`pinDetectedDelimiter`: `ViewState.delimiter` is set and `saveState` posted before the `edit`), and post `edit { baseVersion, change }` where `baseVersion` is the base the edit was **made against** (recorded when the commit started, so a `saved` that arrives while the worker is verifying cannot re-label it). The format controls are locked from the moment of commit (`formatLocked()` = dirty, or an edit in flight) and `refuseWhileLocked()` guards every handler that would re-tokenize. `onSaved` advances the webview's base **immediately** (so an `applyEdits` for an undo that follows `saved` is not mistaken for a gap), then asks the worker to `rebase` with the message's `written`, applies the returned patches to `owner.text`, rebuilds the marks of the written records only (marks of cells edited meanwhile survive; with no `written` it clears all marks), and posts `synced`. `applyEdits` that arrive while a rebase is pending are queued behind it. **Host messages are handled in order around a `load`** (a task that throws is logged with `console.error` and the ones behind it still run): `load` does async work (a frame, the worker's `init`, restoring the pending edits) before the new state is in place, so every host message that arrives after it is queued until that `load`'s `initResult` has been processed. Otherwise an `applyEdits` for an undo sent right after a same-base `load` (a resync) was applied to the old state and then overwritten by the `load`'s `pendingEdits`, which predate it. A regex-timeout worker respawn re-initializes from the original `text`, which would lose the worker's applied edits and drop any in-flight request: after that `initResult`, the main thread re-posts every `editedCells` entry's `current` value in one `setCells` and **re-issues the worker requests that were pending** (`reissuePendingWorkerRequests`: every `workerCalls` entry keeps its request so it can be sent again; a stale `rebase`/`editCell` is answered rather than abandoned).
  - **Host on `edit`**: reject it when the document is `lossy`; drop it (post `load`) when `baseVersion ≠ document.baseVersion` — except a message made against the base just before the last save (`saveBase`, with the document exactly one base further on), which is accepted for any record: the webview made it before it saw `saved`, the save rewrote only the records it wrote, and the edit is applied to the host's own record (for a record the save did write, the record already holds the written baseline, so the message's `originalText`/`originalFields` are not compared; for any other it is checked against the bytes like every edit); drop it with a `load` when `change.format` differs from `document.format` (set on first use), or when `change.record.originalText`/`originalFields` disagree with what the host already holds for that record (or, at the host's own split, with the bytes). Otherwise `records.set/merge` the record, apply `fields[columnIndex] = newValue`, recompute edited-ness; fire `onDidChangeCustomDocument` with `{ document, label: "Edit ‹column›", undo, redo }` where `undo` sets `fields[columnIndex] = oldValue` and `redo` sets `newValue`, each recomputing edited-ness and posting `applyEdits { baseVersion, kind: "undo" | "redo", cells: [{ rowId, columnIndex, value, original }] }` to the panel (`original` = the baseline value, `""` beyond the baseline field count, so the webview can set or clear the mark without asking the worker; the webview forwards `setCells` to the worker, updates `editedCells`, re-renders that cell/field in place and resets `lastQueryKey`; `CellChange.column` names the column for the label). An undo/redo whose captured `epoch` is older than the document's is a **no-op** except for VS Code's own stack bookkeeping: after a clean reload, stale entries can toggle VS Code's dirty flag without any content change; a save in that state writes nothing (next bullet) and the flag clears. Undo after a *save* is not stale: `records` survive the save rebased, so undoing re-edits the record against the saved baseline and the tab becomes dirty again, as in a text editor. `onSaveState` applies the format lock host-side: a `saveState` that changes the delimiter, header flag or quote choice while the document has edits is not stored and answered with a `load`. The one exception is the **pin**: a stored delimiter of `""` (Auto) that becomes exactly the delimiter the document is already being edited under (`document.format.delimiter`) with the same header and quote choices is the same tokenization, so it is stored without touching the records (a document restored from a hot-exit backup is dirty with Auto still stored, and the next edit pins; treating that as a format change made the host keep Auto, reload the webview without the new edit and still accept it, an edit that was saved but never shown).
  - **Save** (`saveCustomDocument(document, token)`), run through `exclusive`: (1) `flushEdits { baseVersion }` is posted to the panel and the host waits up to 500 ms for `flushed { baseVersion }` — the webview commits any open editor and replies after posting its `edit`s, and message order on one channel guarantees they arrive first; a timeout (hidden or busy webview) just proceeds. (2) If the document is not dirty, nothing is written and the save succeeds (this is also what neutralizes the stale-undo dirty flag). (3) Conflict check: `stat(uri)`; if it succeeds and `size`/`mtime` differ from `lastLoaded`, ask (modal, through the `showPrompt` indirection so tests can answer) `"‹name›" has changed on disk since you opened it. Overwrite it with your edits?` with **Overwrite**; anything else throws `Error("Save cancelled: the file changed on disk")`, which VS Code reports as a failed save and the document stays dirty. A missing file is no conflict (recreate). (4) `buildOutput` takes a **snapshot** of the edited records (`{ recordIndex, fields, text }`), splits `bytes`, checks that each record's bytes decode to its `originalText` (`TextDecoder` with `ignoreBOM: true`; any failure or overlap aborts with `Error("CSV Viewer: internal consistency check failed; nothing was written")`), and splices with `spliceBytes`. (5) `workspace.fs.writeFile(uri, out)`; the write is the only `await` that user input can overlap, so everything after it works from the snapshot, never from the live `records`: `stat` → `lastLoaded`; for each *written* record the baseline becomes the snapshot (`originalText` = the text written, `originalFields` = the fields written) and edited-ness is recomputed against it, so an edit or undo that landed during the write stays an edit; `bytes = out`; `saveBase = ++baseVersion`; post `saved { baseVersion, written: WrittenRecord[] }`; if the document is still dirty (late edits), arm the **re-assert**: VS Code marks the document clean when the save promise resolves, so it must be told that it is not, by a content-change event `{ document }` (no undo entry, so the undo stack is untouched). It is sent when the webview confirms the new base with `synced` (which cannot happen before the save reply has left, whereas a timer started at the reply can be batched into the same chunk as it on a socket-based extension host and lose the race), or after 500 ms if the webview never answers (hidden), and not at all if the document is clean by then. Because the event carries no undo entry, the tab stays dirty after it until the next save or revert, even if the user then undoes the late edits back to the saved text; that costs one harmless extra save and is accepted (webview: advance the base, `rebase` with `written` → `rebased` → rebuild marks → `synced { baseVersion }`; a `synced` for a base other than the host's makes it post a fresh `load`). Peak memory during a save is `bytes` + `out` (2× the file); a 512 MB file with a handful of edits saves in a few seconds and is dominated by the write. `saveCustomDocumentAs(document, destination)` (also in the queue): steps 1 and 4 against `destination` (no conflict check, no rebase, document state untouched) — VS Code then re-targets the editor to the new resource itself; verify in real VS Code that the viewer reopens the destination clean and the original document is left as VS Code leaves it. **Save errors** (permissions, provider failures) are thrown with the message `CSV Viewer: could not save "‹name›": ‹error›` and surface through VS Code's own failed-save notification.
  - **Revert** (`revertCustomDocument`): clear `records`/`edited` (bumping `epoch`, resetting `saveBase`); re-read the file (`stat` + `readFile`): on success it becomes the new `bytes`/`lastLoaded`; on failure (deleted) the held `bytes` stay; either way `baseVersion++` and a fresh `load` (empty `pendingEdits`) is posted. VS Code calls this for Revert File, for "Don't Save" on close, and via the changed-on-disk banner's button: the host handles the webview's `revert` message by `webviewPanel.reveal()` then `vscode.commands.executeCommand("workbench.action.files.revert")` — the only route that also resets VS Code's dirty flag and undo stack. Verify in real VS Code that the command reaches `revertCustomDocument` for an active custom editor; if not, the fallback is to leave the banner without the button and document "use File → Revert File".
  - **Backup / hot exit** (`backupCustomDocument(document, context, token)`): writes JSON `{ version: 1, fingerprint: { size, mtime }, format, records: [{ recordIndex, originalText, originalFields, fields, floor }] }` for the edited records to `context.destination` and returns `{ id: context.destination.toString(), delete() }`; the backup is small (the edits, not the file). `openCustomDocument` with `backupId`: read that JSON (`version` must be 1; anything else is ignored with a `console.warn`), read the file, and restore `records`/`edited` (a missing `floor` defaults to `originalFields.length`) **only if** the file's `stat` matches `fingerprint` — otherwise drop them and warn `CSV Viewer: the unsaved edits to "‹name›" couldn't be restored because the file changed.` VS Code treats a document opened from a backup as dirty on its own (`_fromBackup`; verify — if it does not, fire one `onDidChangeCustomDocument` content event `{ document }` without undo/redo); restored edits have **no undo entries** (the stack is not persisted), only Revert or editing them back. The first `load` then carries `pendingEdits: { recordIndex, originalFields, fields }[]`; after its `initResult` the webview posts one `setCells` for them and the worker checks each record's unpadded parsed fields against `originalFields` — mismatching records are reported back via `editsDropped { recordIndexes }` (host removes them and warns once naming the rows; the webview itself shows no banner) and the rest set marks as usual.
  - **Undo and redo keys inside an open editor.** VS Code's webview host script (`webview/browser/pre/index.html`) calls `preventDefault()` on Ctrl/Cmd+Z / Y keydowns and forwards them to the workbench, which runs `undo`/`redo` — for an active custom editor that is the document stack above. That is exactly right with no editor open. With an editor open it would discard the user's typing and undo the previous *committed* edit, so the editor's own `keydown` handler calls `ev.stopPropagation()` (not `preventDefault`) for those keys: the host script's listener is attached to the content window and sees nothing, the browser's native text undo runs in the field. **Verification.** The argument from VS Code's source is that the host script's `keydown` listener on the content window is a bubble-phase listener, so `stopPropagation` from the field keeps it from forwarding the key. The integration test "Ctrl/Cmd+Z typed inside an open editor stays in the editor; with no editor open it reaches the document's undo" checks it end to end with **real key presses**: VS Code (1.125 and later) drops forwarded keys that are not `isTrusted` (`shouldForwardKeyEvent`), so a `KeyboardEvent` built by the page proves nothing, and the test VS Code is therefore launched with `--remote-debugging-port` (`runTest.ts`, port passed to the tests in `CSV_VIEWER_CDP_PORT`) and the test talks to it directly (`src/test/integration/cdp.ts`, Node's global `WebSocket`, no dependency): it lists the debugging targets (`Target.getTargets`: the workbench `page`, and webview frames that run out of process show up as separate `iframe` targets), attaches to each (`flatten: true`), walks each target's frame tree (`Page.getFrameTree`), and looks for the selector in every frame through an isolated world (`Page.createIsolatedWorld` + `Runtime.evaluate`), so it works whether the webview's frame is in the workbench's process or not. It focuses the element in that frame and sends `Input.dispatchKeyEvent` (`rawKeyDown` + `keyUp`, with `key`, `code`, `windowsVirtualKeyCode` and the Ctrl/Meta modifier bit) first on the frame's own session and then on the pages' sessions, taking the first after which an observer installed in the frame saw the `keydown` (so a key is never sent twice, and a key that never arrives is an error rather than a silent pass). If an element cannot be found, the error lists `/json/version`, `/json/list`, every target and every frame with its parent and what it matched. It first opens an editor and asserts the document's edit count is unchanged, then closes it with Escape, focuses a grid row and asserts the same key now undoes the edit; the second half is the positive control that makes the first meaningful. The driver was checked against a plain Chromium with a cross-origin iframe that is out of process and with one that is in process (trusted `keydown` with `code: KeyZ` arrives in the frame either way); the VS Code half has only been run by CI. Fallback if it fails in a given VS Code version: the `editorState` / `csvViewer.cellEditing` context-key scheme — the webview posts `editorState { open: boolean }`, the host mirrors it into the context key, and package.json contributes `ctrl+z` / `cmd+z` → `csvViewer.inlineUndo` and `ctrl+shift+z` / `cmd+shift+z` / `ctrl+y` → `csvViewer.inlineRedo` with `when: activeCustomEditorId == csvViewer.table && csvViewer.cellEditing`, whose handlers post `inlineUndo` / `inlineRedo` to the webview, which runs `document.execCommand("undo" | "redo")` in the focused field. Either way the observable contract is the one in section 6.
  - **Visibility re-sync.** `panel.onDidChangeViewState` → when the panel becomes visible and the webview's last `synced` base is not `document.baseVersion`, the host posts a full `load` (with `pendingEdits`), which is always safe; this covers any `saved`/`load` that was posted while the panel was hidden and not delivered.

The test moves its own fixture (`move-viewer.csv`) and waits for a render count rather than for "a render", because the shared per-file message log would otherwise satisfy the wait with the previous panel's render.
  - **Message types** added to `src/core/types.ts` (webview ↔ host) and `src/webview/workerProtocol.ts` (webview ↔ worker) are exactly the ones named in this section (plus `editsDropped` webview→host, `editRefused { message }` host→webview, `applyEdits.kind`, `SavedMessage.written` (with each record's `floor`), `LoadMessage.recordFloors`, the worker's `init.floors`, `CellChange.column`, and `synced`, which the webview now posts after every `load` as well as after a save); `CellChange`, `RecordInfo` (the `record` object above), `PendingRecordEdit` (`pendingEdits` entries) and `ReadOnlyReason` live in `src/core/types.ts` so all three bundles share them.

## Non-goals (0.8.0)
- Adding, deleting, duplicating, moving or reordering rows; adding, deleting, renaming or reordering columns; editing header cells (with "First row is header" on).
- Multi-cell operations: range selection, fill-down, find-and-replace, paste of a block of cells, editing while a filter re-applies live, bulk edit from the values picker.
- A cell-focus keyboard model (arrow keys between cells): the roving unit stays the row; F2 + Tab and the per-field edit buttons are the keyboard routes.
- Preserving the original quoting of *unedited fields inside an edited record* (the record is re-serialized whole), or an embedded CRLF inside a quoted field of an edited record (it is written as LF, as it was parsed).
- Encoding detection or any encoding other than UTF-8 (a non-UTF-8 file opens read-only); writing a BOM that wasn't there, or removing one that was.
- Editing files over the 512 MB limit, or editing values over 1 MB in place.
- Reflecting a text editor's unsaved buffer in the viewer, or the viewer's unsaved edits in a text editor, or any three-way merge when both are dirty.
- Changing the delimiter, header or quoting options while the document is dirty (they lock instead).
- Multiple viewer panels on one document; collaborative or Live Share editing.
- Per-cell validation or typed cells (numbers, dates): every value is text, as before.
- An "Edit mode" toggle in the toolbar, a visible dirty counter, or a diff/preview of the pending changes before saving (VS Code's tab dot and undo stack are the UI).

### Hotspots (function-level evidence)
1. **One row, two million columns (the "20 MB single line" super-linearity) — main thread DOM, not the parser.** The fixture (`writeSingleLongLineCsv`: `header\n` + `xxxxxxxxx,` repeated) has one data row of N ≈ bytes/10 fields, so `parseCsv` produces N headers (`column_N`). Playwright, HEAD: 1 MB (104,858 columns) 5.3 s, 2 MB (209,716) 10.5 s, 4 MB (419,431) 23.7 s — ≈ linear per column but at ≈ 55 µs per column, and the DOM holds exactly **4 nodes per column** (419,628 / 839,060 / 1,677,920 elements): `renderColumnsPopover` (a `label` + `input` + `span` per header, rebuilt on every `initResult`) and `renderSortPopover` (an `option` per header, rebuilt on **every** `finishRender`), both for popovers nobody opened; each filter rule's column `select` adds N more. Main-thread self time at 4 MB (26.3 s sampled): `createElement` 3.5 s, `appendChild` 1.9 s, forced layout via `clientWidth` 1.9 s, `renderColumnsPopover` 1.3 s + `renderSortPopover` 1.3 s own time, `addEventListener` 0.4 s, the `columnVisibility` object 0.9 s (`setColumnFlag` → `Object.defineProperty` per header, `hasColumnFlag`, `sameColumnVisibility`), GC 0.8 s, and 4.6 s of Playwright's own selector polling over that DOM (test artefact). Timeline at 4 MB: worker `init` 0.8 s; `onInitResult` 5.2 s before the first `query` is even posted; the main thread is then busy for 2.2 s (style/layout of the new subtree and, in this harness, Playwright's selector polling over it) before it reads `queryResult`; `finishRender` 6.5 s. Per render the code also builds `new Map(state.headers.map(…))` **per row** in `buildRowTr` and `populateDetailContent` (1.3 s per call at 1.6 M headers) and calls `visibleColumns`/`detailOnlyColumns` (full header scans) per render. A 20 MB line (2.1 M columns) extrapolates to ≈ 8.4 M DOM nodes and > 100 s, which is the hang. The worker side is linear but heavy: node `parseCsv(auto)` at 8/16 MB = 2.1/4.3 s, of which `dedupeNames` ≈ 60 % (`new Set(names)` 0.37/0.89 s, the `firstIndexOf` Map 0.38/0.74 s, the `used` Set and `names.map` the rest), `rawNames` template strings 0.15/0.58 s, Papa itself only 0.13/0.47 s (0.07/0.19 with the delimiter given), `profileColumns` 0.49/0.87 s (≈ 45 % of it `looksLikeMarkdown` running nine regexes on 9-character cells). `reconcileVisibility` 1.0/3.6 s and `JSON.stringify(columnVisibility)` 0.46/1.5 s (posted to the host in every `saveState`, and persisted by VS Code to `workspaceState` each time). `splitRecordsToTable` 28/70 ms. Nothing here is O(n²); `String.prototype.indexOf` over `headers` would be (2,000 lookups over 839k headers = 49 s) but no such loop runs on this path — the candidates named in the brief (`recordSpans`, Papa options, `truncate`, JSON detection, DOM text measurement, CSS layout of a huge cell) are all linear or not on the path (cells are 9 characters; `truncate` is µs; `clippedVisibleColumnsForRow` runs only for expanded rows).
2. **The deferred span job rescans the text once per slice (the 0.8.0 regression).** For texts over `SYNC_SPANS_MAX_CHARS` the worker runs `scanRecords(text, …, job.pos, SPAN_SLICE_RECORDS)` repeatedly from `stepSpanJob`/`ensureSpans`. Every call starts with `nextDelim = nextLF = nextCR = -1`, so a terminator or delimiter that does **not occur** in the text (`\r` in an LF file, `\n` in a CR file, `;` on the semicolon re-parse of a comma file) is searched with `indexOf` from `pos` to the end of the 60 M-char text on *every* slice (≈ 200 slices × 60 MB). Chrome worker trace at 200k × 30: `stepSpanJob` 1,171 ms inclusive, **1,090 ms self in `indexOrEnd`**, against 114–126 ms for the same scan in one call (node: LF/`,` sliced 393 vs one-pass 126 ms; LF/`;` 550 vs 24; CRLF/`;` 315 vs 24; CRLF/`,` 81 vs 87 — the only case where every needle occurs). The job runs in 8 ms slices behind `setTimeout(0)` (Chrome clamps nested timers to 4 ms, so it occupies the worker for ≈ 2 s after every large parse), which is exactly when the user sorts or filters: that is the +75 ms sort, +126 ms separator and +20 ms page deltas above (`spansReady` arrived ≈ 650 ms after first render in the profiled run). `addByteOffsets` is lazy (first edit or rebase) and the worker's `text` is the deserialized `init` string, not a copy — neither is on the first-render path, so "record spans, byte offsets, retained text" is refuted except for this slice bug.
3. **Papa's delimiter guess on the whole text** (auto mode, the default): 93–140 ms of the ≈ 600 ms `init` at 200k × 30 (node `Papa.parse` auto 632 vs delimiter-given 470 ms; quoted variants 713 vs 663 and 1120 vs 1058). The same guess on a 64 KB prefix cut back to a newline takes < 1 ms and returned the identical delimiter for all three `samples/` files and six synthetic fixtures (comma/semicolon/tab/pipe, quoted, quoted multi-line first rows, the single-line file).
4. **`idByRowRef`**: a 200k-entry `Map<string[], number>` built on every `init` (60–96 ms) only so `onQuery` can turn `applyFilters`' row arrays back into ids (another 200k `Map.get`s). An id-returning filter over the same rows measured 6 ms for the empty first query vs 72 ms for Map + `applyFilters`, and 306 vs 376 ms for a quick search.
5. **Forced layout in `renderTableBody`**: 138 ms on first render, 17–61 ms on every re-render (`get clientWidth` is the top self-time entry in the sort, separator and quick-search profiles after idle).
6. **`normalizeLineEndings`** runs `replace(/\r\n|\r/g, "\n")` over the whole text on every parse: 38–41 ms (node) / 77 ms for two parses (Chrome) on a text with no `\r`; `text.indexOf("\r")` takes 7 ms.
7. **Extension host, 120 MB / 12 columns (harness, node 22)**: `workspace.fs.readFile` copy 303 ms; `decodeText` (`TextDecoder` fatal) 103–122 ms; **`JSON.stringify` of the `load` message 1,568 ms and `JSON.parse` 228 ms** — VS Code's `Webview.postMessage` JSON-serializes everything except `ArrayBuffer`s/typed arrays, which it ships as binary attachments (`engines.vscode ≥ 1.57`; ours is `^1.80.0`); then the renderer structured-clones the string into the webview iframe and the webview clones it again into the worker (≈ 40 ms per 60 M chars). That chain, plus one more transient 120 MB string in the host, is the CI "5.2 s open, RSS +328 MB" (bytes 120 + decoded text 120 + JSON ≈ 120, the latter two transient). Save (`buildOutput`) CPU: decode again 103–122 ms, `splitRecordsToTable` 169–264 ms, `SpanTableBuilder` doubling copies + `finish()` slices ≈ 175 ms (1.4 M records), the `[^\x00-\x7f]` test in `addByteOffsets` 84–95 ms (376–580 ms for a non-ASCII file, which takes the `utf8Length` pass), `spliceBytes` 80 ms, `TextEncoder` 10 ms ≈ 0.6 s before the write; the harness's 2.4 s "save" is 1.8 s of GC from hosting the worker's 1.4 M rows in the same heap and is not an ext-host number. The first edit of a large file costs one full span scan + byte offsets in the worker (366 ms at 120 MB), as designed.

**Not hotspots (measured, leave alone):** `profileColumns` at 200 rows (3 ms); `looksLikeMarkdown`/JSON detection on wide files; `truncate*`; DOM text measurement; `buildColumnSortKeys` (80–131 ms per column, cached) and `sortRowIdsByCachedKeys` (6–16 ms); `applyFilters` with a `contains` rule (41–57 ms); `distinctValues` (51 ms); the main→worker clone (≈ 40 ms; the one 372 ms `postToWorker` sample in a profiled separator step did not recur in ten unprofiled runs, 35–49 ms each, and coincided with a major GC); webview boot (82–190 ms from `setContent` to `ready`; `main.js` 355 KB, `worker.js` 72 KB, `extension.js` 51 KB); the worker's retained `text` (a reference). Quick search (`foldCase` per cell: 173 ms in Chrome, 312–335 in node for 200k × 30) could be halved with a case-insensitive `RegExp` (147 ms) but that regex does not fold `ß`→`ss` or `İ`→`i` as `foldCase` does, so a fast path would need a per-cell "contains ß/İ/U+0307" pre-test; it is within target (≈ 45 ms at 50k rows) and is **not** part of this pass.

### Performance pass, part 2
Profiled on `f31d81b` (the 0.8.1 build) with the part-1 tooling: cross-thread timeline, CDP `Profiler` on the main thread, a per-thread Chrome trace for the worker, `node --cpu-prof` over `src/core`. The Playwright harness still posts `text`, so these numbers are the `text` path; the bytes path VS Code takes adds a 53 ms `TextDecoder.decode` on the main thread (measured, 60 M chars) before the same clone.

**Where the ≈ 720 ms of in-page first render goes (200k × 30, load received → first row).**
- Main thread, on the critical path ≈ 75 ms: `onLoad` to `init` posted 4 ms (the worker is pre-warmed); `postToWorker` **50 ms** (structured clone of the 60 M-char string; 42–51 ms self in every profile); `onInitResult` + query/page bookkeeping ≈ 5 ms; `finishRender` **15 ms** (down from 190 in 0.8.0). GC 128 ms over the run, almost all of it the harness's own string churn. Nothing left to cut on this thread except the clone (and, under VS Code, the decode).
- Worker, critical path ≈ 610 ms: deserializing the cloned string ≈ 40 ms (`init` is received 89 ms after it is posted); `onInit` 468 ms inclusive = `parseCsv` 444 (Papa `Parser.parse` **362 ms self**, `processResults`/`pushRow` ≈ 10, `normalizeLineEndings` 14 — the `indexOf("\r")` over 60 M chars —, delimiter guess < 1, `parseCsv`'s own slice/maxCols/map 25) + `profileColumns` 2 + posting `initResult` 1; plus the share of GC that lands inside the parse (the Chrome trace books 460 ms of worker GC over the whole scenario; in node a lone `parseCsv` is 380 ms of attributed time inside 869 ms of wall, the rest scavenges of the 6 M new cell strings). Then `query` (`filterRowIds` 6 ms) and `page`, 31 ms including four message hops.
- Papa is near the floor. node, same fixture: Papa with the delimiter given 568 ms; a bare `text.split("\n")` then `line.split(",")` per line (which is exactly Papa's fast mode) 455 ms; `fastMode: true` forced 489 (noise-level, and Papa already takes fast mode whenever the text has no `"`; forcing it with quotes present is wrong); `skipEmptyLines: false` no faster. Papa's overhead over the floor is ≤ 25 %, and the floor is the cost of materializing 6 M strings. `profileColumns` reads 200 rows (1–3 ms): there is no second pass worth merging.

**Where the ≈ 416 ms of the separator step goes** (`;` on a comma file, one column out): ≈ 100 ms is Playwright driving the popover and select; `postToWorker` clone **42 ms** + worker deserialize ≈ 40 (`init` received 79 ms after the post); worker re-parse **149 ms** (Papa splits 200k lines on `;`, one cell each, then `rows.map`); `query` + `page` 40 ms; render + visibility poll ≈ 70 ms. The re-parse clones a string the worker already holds.

**Optimizations (ranked; each: change → gain → risk → equivalence test).**

1. **Progressive parse: parse by record slices and show the first page after the first slice.** The worker's `onInit` runs `scanRecords` on the original text in slices of `PARSE_SLICE_RECORDS = 2048` records (the same resumable scan that builds the span table today, so the deferred span job disappears: `builder.push` and the parse share one pass) and parses each slice standalone: `Papa.parse(normalizeLineEndings(text.slice(sliceStart, sliceEnd)), { delimiter, newline: "\n", quoteChar, skipEmptyLines: true, header: false })` with the delimiter from the prefix guess and `sliceEnd` *after* the slice's last terminator; rows are appended to `rawRows` in order. Per slice, `parsed.data.length` must equal the number of records the scan emitted for it; on the first mismatch the worker abandons the slices and runs today's whole-text `parseCsv` (kept as the fallback and the test oracle), with `spansOk` as today. `initResult` is posted after slice 1 with the headers taken from it, `totalRows` = rows so far, `parsing: true`, and — when the view state has no sort keys, filter rules or quick search — `firstPage: { page, rows }` for `pendingPageAfterQuery` (so no `query`/`page` hop); the remaining slices run through the existing `MessageChannel` stepping (8 ms budget); `parseDone { requestId, totalRows, headers, spansOk }` follows, and the main thread re-reconciles visibility only if `headers` changed (a ragged file whose widest row came later: `maxCols` is final only at the end, short rows are padded then, as `parseCsv` does). Everything that needs the whole table — `query`, `distinct`, `editCell`, `setCells`, `rebase` — first calls `ensureParsed()` (finishes the remaining slices synchronously, like `ensureSpans`); the main thread shows the pager with `Loading…` in place of the total and keeps the toolbar enabled; a `query` posted before `parseDone` (saved sort/filter) is answered after it, as the working indicator already covers. `quoteProblems` are the first 20 quote-error rows with each slice's row offset added. **Gain:** node, first slice (scan + Papa, 2,048 records) **13 ms** unquoted / 17 ms with a fifth of the cells quoted; in-page first render ≈ 720 → **≈ 200–250 ms** (transfer 90, normalize + guess ≈ 15, slice 13, profiles 2, render 15, hops ≈ 20, plus the GC that falls in). Total worker CPU: slice-wise 613 ms vs whole-text Papa 568 + the span scan 209 it replaces (−9 %) on the unquoted fixture, 927–1,077 vs 711 + ≈ 250 on the quoted one (−5…+12 %); the `spansReady` pass as a separate job is gone. **Risk:** rows must equal the whole-text parse. Papa's per-record tokenization depends on nothing outside the record (its `extraSpaces` look-ahead stops at the record's own delimiter or terminator, which is why each slice carries its terminators), the scanner reproduces Papa's record boundaries (the 0.8.0 property tests and the runtime `spansOk` check), and a count mismatch falls back to the old parse, so the only way to show different cells is a boundary agreement with different cell content, which the equivalence test below searches for. Editing sees no change once `parseDone` has run: row ids are indexes, spans come from the same scan, `floors`/`originals`/the per-commit re-parse are untouched; an edit that arrives earlier finishes the parse first. User-visible: a large file shows its first page before its row count; a ragged file may gain columns after first paint. **Verify:** fast-check property in `csvParse.test.ts`: for random texts (quotes, `""`, malformed quotes, CR/LF/CRLF/`\n\r` mixes, BOM, blank and whitespace-only lines, ragged rows, multi-character delimiters, quotes off with and without NUL) and slice sizes 1…n, `parseProgressive` ≡ `parseCsv` in `headers`, `rows`, `delimiter`, `quoting`, `quoteProblems`, and its span table ≡ `splitRecordsToTable`; `workerEdit.test.ts` adds an `editCell` sent before `parseDone`; `scale.spec.ts` asserts `initResult` within the strict budget below and that the final `Showing … of 200,000 rows` arrives; `largeFile.spec.ts` covers the ragged case (a wider row after the first slice adds its `column_N` headers and the Columns popover updates).
2. **Hand the worker the bytes and keep bytes, not text, on the main thread.** `init` carries `bytes: ArrayBuffer` (transferred; `text` stays accepted for the Playwright harness) and the worker decodes it (`new TextDecoder("utf-8", { ignoreBOM: true })`, non-fatal — the same string the main thread decodes today) and hands the buffer back, transferred, in `initResult` (`bytes`), so neither side copies it; `state.text` becomes `state.bytes` and the file-sized JS string leaves the main thread's heap. The separator, header and quote controls post `reparse { requestId, options, floors }` and the worker re-parses its retained `text` (same `initResult`); a regex-timeout respawn posts `init` with the bytes again. After `rebased`, the worker also returns `bytePatches: { byteStart, byteEnd, bytes }[]` (its byte offsets exist by then — `ensureSpans(true)`), the main thread splices its buffer with a `spliceByteReplacements` next to `spliceBytes` in `csvEdit.ts`, and `byteLength` stays known after a save (today it is dropped). **Gain (measured pieces):** main thread −50 ms clone (and −53 ms decode under VS Code) on every load; worker decode of a transferred 60 MB buffer 41 ms vs ≈ 40 ms deserializing the clone (neutral); format changes −80…−120 ms (no clone, no deserialize: 149 ms of parse remain); main-thread JS heap −60 MB at 200k × 30; the `applyTextPatches` on the UI thread after each save (70–80 ms at 120 MB) becomes an 80 ms splice of bytes, neutral. **Risk:** the respawn and save paths now depend on the byte patches being exact. **Verify:** property test `decode(spliceByteReplacements(bytes, bytePatches)) === applyTextPatches(text, patches)` over random edits; `editingRaces.spec.ts` (respawn during a rebase, undo after `saved`) and `hostSave.test.ts` unchanged; `scale.spec.ts` gains a bytes variant (`new TextEncoder().encode(text)` in the page before the clock starts, posted as `bytes`) so the measured path is VS Code's.
3. **First page with `initResult`** is part of item 1; on its own (no sort/filter/search in the view state) it saves the two `query`/`page` hops and `filterRowIds`, ≈ 25–30 ms, and is safe (`latestQueryRequestId`/`latestPageRequestId` take the init's id; a stale `pageResult` is dropped as today).

**What cannot reasonably be cut further.** Papa's parse (≈ 360–400 ms worker CPU at 200k × 30) plus V8's scavenges of the 6 M cell strings it creates are within 25 % of a bare `split`; a custom tokenizer or a flat cell store would rewrite every consumer of `string[][]` for at most that margin, so item 1 moves the cost off the first paint instead of shrinking it. The remaining fixed costs are the ≈ 90 ms it takes a 60 MB string or buffer to cross into the worker (item 2 removes the main-thread half), four message hops (≈ 20–30 ms), the 15 ms render, and Playwright's own visibility poll. The separator re-parse keeps its 149 ms: Papa does not expose its line split for reuse, and the result is one column per row anyway.

**Revised targets.** With items 1–3: in-page first render at 200k × 30 **< 400 ms strict** (expected 200–250 here; the 0.8.1 target of 800 stays as the generous×2 CI bound's base); separator/header/quote re-parse **< 500 ms strict** (expected ≈ 250–300 including the test driver); the full parse (`parseDone`) is logged, not bounded (≈ 600–700 ms of worker CPU is the floor above). With item 2 alone: ≈ 650 ms first render, ≈ 300 separator. What the implementation settled:
- **`ProgressiveParse`** (`src/core/progressiveParse.ts`) is the class the worker steps; `parseProgressive` runs it to the end for tests. Slice size is a constructor argument and, through `init`/`reparse` `tuning` (read from `window.__csvParseTuning` under testHooks), a delay between slices too.

Delimiters Papa cannot use become `,` as in Papa. Later slices start with a blank line so a leading U+FEFF is not taken for a byte order mark. Error rows are Papa's unfiltered row indexes, offset by the rows of the slices before.
- **The delimiter guess** on a CR-containing text normalizes only the first ten lines unless a quote is among them; a text with no CR is searched once, and the scan reuses that answer.
- **First page:** only when the view has no sort, filter, search, edits or pending edits, page 1 is wanted, the parse did not finish in slice 1 and the rows so far fill the page. A file parsed in one slice (most small files) keeps the query/page round trip, so those tests are unchanged.
- **While parsing** the pager shows `…` for the page count and `1–100 of … rows (loading)`, its buttons are disabled, the status line says how many rows are shown, and the test-hook `rendered` message waits for the count (sent at `parseDone`). Sort, filter, search, the values picker, an edit, `setCells`, `rebase`, and a page size too large for the rows so far all make the worker finish the parse first, so their answers cover every row. A ragged file's headers and profiles are sent again at `parseDone` when its widest row came late (or when the first slice held fewer rows than the profiles sample), and the page is fetched again.
- **Bytes:** the main thread keeps `state.bytes` (null while the worker holds the buffer; the init result hands it back, matched by the request that sent it so a stale result of the same load still returns it). Harnesses that post text are encoded on the main thread, so the e2e suite runs the bytes path; a lone surrogate in such a text becomes U+FFFD. `rebased` carries `bytePatches`; the worker's byte length stays known after a save.

- **A rebuilt parse cannot misdirect an edit.** `editCell` carries the value the sender saw (`expected`); the worker refuses, with `stale`, when the cell holds something else, and the page shows the edit-error banner and asks the host for a fresh load (`resync`). ### Performance pass, part 3
Three targets of parts 1–2 were still unmet at `9b6e665`; each was profiled with the part-1 tooling (harness RSS accounting under `--expose-gc`, CDP main-thread profiles, a per-thread Chrome trace, node benches of `src/core`), and VS Code's serialization path was read from `microsoft/vscode` `main` (the `release/1.139` branch does not exist; the files involved are unchanged in substance since the 1.57 buffer support).

**1. Extension-host RSS growth on a 120 MB open: 1.99× the file.** The extension's own code holds exactly one file-sized buffer: in the harness, `arrayBuffers` grows by 120 MB at `readFile` and by 13 MB (the span table) at the load, and `load.bytes` is `document.bytes.buffer` itself (`sameBufferAsDocument=true`). The second copy comes from how VS Code hands the file over, and the extension then adds a third, transient one. `workspace.fs.readFile` for the `file` scheme returns `(await this._proxy.$readFile(uri)).buffer` (`extHostFileSystemConsumer.ts`), i.e. the RPC reply's `VSBuffer`, which `MessageBuffer.readVSBuffer` (`rpcProtocol.ts`) makes with `this._buff.slice(offset, …)` — `VSBuffer.slice` is `subarray` ("use subarray instead of slice", `base/common/buffer.ts`) — so `document.bytes` is a **view at `byteOffset` 9** (1 message-type byte + 4 request + 4 length) into the message buffer `ChunkStream.read` allocated for the whole reply (`ipc.net.ts`: a reply spanning several socket chunks lands in one `VSBuffer.alloc(byteCount)`). `arrayBufferOf` sees the non-zero offset and does `bytes.slice()`: measured 112 ms and +120 MB `arrayBuffers` for a 120 MB offset view (`hostView.test.ts`). That copy is then wrapped without copying by `serializeWebviewMessage` (`VSBuffer.wrap(new Uint8Array(arrayBuffer))`, `extHostWebviewMessaging.ts`) and copied once more by the RPC layer into the outgoing request (`MessageBuffer.writeMixedArray` → `writeVSBuffer`, `rpcProtocol.ts`) — VS Code's copy, not under our control; the renderer side allocates its own (`deserializeWebviewMessage`: `new ArrayBuffer(byteLength)` + `set`) and transfers it into the iframe. So the ext host peaks at 3× (retained view + our slice + the RPC message) and settles at 1× once the two transients are collected; the integration test reads RSS right after `rendered`, before that, and sees ≈ 2×.
- **Change:** `postLoad` posts the `Uint8Array` itself — `bytes: document.bytes` — and `arrayBufferOf` is deleted. `serializeWebviewMessage` handles views (`ArrayBuffer.isView` → the underlying buffer plus `{ byteOffset, byteLength }`), and `deserializeWebviewMessage` recreates `new Uint8Array(arrayBuffer, byteOffset, byteLength)` in the renderer, so the webview receives a `Uint8Array` whose buffer is 9 bytes longer than the file. `LoadMessage.bytes` becomes `Uint8Array | ArrayBuffer` (the harnesses keep posting an `ArrayBuffer`); `onLoad` normalizes to a view (`bytes instanceof ArrayBuffer ? new Uint8Array(bytes) : bytes` — never `new Uint8Array(view)`, which copies), passes `byteLength` = the view's length, transfers `view.buffer` to the worker with `byteOffset`/`byteLength`, the worker decodes `new Uint8Array(buffer, byteOffset, byteLength)` and hands the buffer back as today; `state.bytes` stays a view, and `spliceByteReplacements` works on the view (the replacement buffer is exact-sized, so the offset disappears after the first save). The host side is unchanged otherwise: `buildOutput` already splits `document.bytes` as a view. **Gain:** one file-sized transient copy and ≈ 110 ms per load gone from the extension host; the remaining second copy is VS Code's RPC message (code above). **Risk:** none to the bytes written — the view is the same bytes the host splits at save; the only new failure mode is reading the 9 header bytes by using `buffer.byteLength` where the view's length is meant, which the equivalence test below catches. **Verify:** `hostSave.test.ts` and `workerEdit.test.ts` run with a `readFile` stub that returns a subarray at offset 9 of a larger buffer (the fake `readFile` gains an option; the existing byte-exact save and rebase tests then exercise the offset), plus a property test that `load.bytes` as posted equals the file for random offsets; `opening.itest.ts` asserts a BOM + non-ASCII + CRLF fixture renders the same cells (the real `deserializeWebviewMessage` path).
- **Corrected target:** `largeFiles.itest.ts` keeps the 3× gate on the immediate reading and logs it; the 1.5× figure is replaced by a **settled** reading, the minimum of `process.memoryUsage().rss` sampled once a second for five seconds after `rendered` (expected ≈ 1.1× with the change; the RPC copy is freed by the next major GC and glibc returns mmap'd blocks on free), logged with the 2× figure from VS Code's copy as its explanation. `external`/`arrayBuffers` are logged alongside RSS, since they count live backing stores only.

What the implementation settled, and where it departs from the plan above:
- **Item 1 as planned.** `document.bytes` is posted as it is; the host harness's fake `readFile` now returns a subarray at offset 9 of a larger buffer **by default** (not behind an option), so every host test (`hostSave`, `workerEdit`, `loadBytes`, the fuzzers) reads a view; the harness clones the whole backing buffer for the "webview", as `postMessage` does, so a receiver that ignores `byteOffset` reads the wrong bytes. `loadBytes.test.ts` asserts `load.bytes.buffer` is the `readFile` buffer (no copy) with the offset and length intact; `workerParse.test.ts` has the property that decoded text, page rows, edit offsets, `bytePatches` and the spliced bytes are identical for a view with random slack before and after and a plain buffer, and that the worker leaves the view's bytes alone. The worker's `init` request and `initResult` carry `Uint8Array`s (the `ArrayBuffer` form is accepted only by `onLoad`, which wraps it without copying). The copy that is gone was measured earlier at 112 ms and +120 MB for a 120 MB offset view; the RSS reading in a real extension host is the integration job's (`largeFiles.itest.ts`: the immediate 3× gate is kept, and a settled reading, the minimum RSS over five one-second samples after `rendered`, is gated at 1.5× the file and logged with `external` and `arrayBuffers`; it has not been run here, so 1.5× is the plan's expectation of ≈ 1.1× plus margin for a collector that is slow on a shared runner, not a measured value).
- **Item 2: only the blank test and bound `compare` landed.** Sorting a `string[]` of the text cells and ranking from it needs a text → rank `Map` over 200k distinct strings (200k sets and 200k gets), and measured 170 ms against 100 ms for the index sort on the sorted-ish scale fixture (and 920 against 1,100 on a shuffled one, where the sort dominates); sorting the key objects directly was within noise of the index sort. So the more-than-20,000-distinct path keeps its index sort; the few-distinct path (already a `string[]`) now sorts with the collator's bound `compare`, and both use it for the rank walk. `cellSortKey` tests blankness by char code (`isBlank`, exactly the characters `trim()` removes; checked against `trim()` for every UTF-16 code unit and for random whitespace-heavy strings), which is where the measured gain is: 10 ms of a 110–120 ms key build, 17 vs 34 ms for the 200k classifications alone. The ranks themselves are pinned against an independent definition (number of collator classes strictly below), through both paths including 20,001 distinct values.
- **The filter cache** keys on `filterCacheKey(headers, quickSearch, rules)` (`src/core/filter.ts`): the quick search plus, for the rules that are enabled and `isRuleActive`, the column, operator, value, `values` (for `in`), mode and case flag; disabled or inactive rules and rule ids are not in it. The cached ids are never mutated (sorting copies), and `queryResult` carries `filterCached` so tests can see a hit. It is dropped in `beginParse` (init and reparse), after every parse slice and at `parseDone`, whenever a cell changes (`invalidateColumn`, which `editCell` and `setCells` both call) and at `rebase`. `workerFilterCache.test.ts` runs random sequences of queries (with and without changing only the sort), edits, `setCells`, rebases, reparses and inits against a model of the rows that filters and sorts afresh; it also requires that nothing stale is served after a change and that an unchanged search over unchanged rows is a hit (the property asserts more than a hundred hits and as many misses over its run). Removing the cell-change, the `rebase` or the parse-start invalidation each fails it; the per-slice and `parseDone` ones cannot be told apart from the first by any message sequence, since a query finishes the parse before it fills the cache, and are kept as the cheap guard against a future query that does not.
- **Item 3 as planned.** `LoadMessage.text` and `onLoad`'s text branch are gone (there was no lone-surrogate replacement in `onLoad` itself; the one in the e2e harness is `TextEncoder`'s).
